# エージェント使用ガイドライン

このドキュメントでは、各エージェントの使用方法と最適な活用戦略を定義します。

---

## project-orchestratorエージェント（最優先）

### 🎯 新規タスク受領時の必須手順

- ユーザーから新規の指示・タスクが来た際は、**まずproject-orchestratorエージェントを起動**してプロジェクト管理を行う
- 複雑なタスクや複数のステップが必要なタスクは、必ずproject-orchestratorで計画・分解・管理する
- 単純な質問や1ステップで完了する小規模タスクのみ、直接対応可能

### 📊 タスク完了時の報告義務

- 各エージェント（japanese-coding-specialist、Code-Reviewerなど）がタスクを完了した際は、**必ずproject-orchestratorに報告**する
- 報告内容: 完了したタスク、実施内容、発生した問題、次のステップの提案
- project-orchestratorは全体の進捗を管理し、次のタスクを割り当てる

### 使用例

```
ユーザー: 「新機能を追加してほしい」
→ まずproject-orchestratorを起動してタスク分解・計画
→ 各フェーズごとにjapanese-coding-specialistに依頼
→ 各フェーズ完了後、project-orchestratorに報告
→ project-orchestratorが次のフェーズを指示
```

## japanese-coding-specialistエージェント

### 基本的な使用方法

- **コーディング作業（新規作成、修正、デバッグ、リファクタリング等）はすべてこのエージェントを使用**
- **小規模な修正の場合**: 単一のタスクとして依頼可能
- **依頼時の注意**: 各フェーズ完了後に動作確認を行ってから次のフェーズに進む
- **タスク完了時**: project-orchestratorに完了報告を行う

### 大規模タスクのフェーズ分割戦略

**コンテキストウィンドウが溢れるのを防ぐため、必ずフェーズごとに分けて依頼する**

#### 分割の基準

1. **コンテキストウィンドウ制約**: 1フェーズで読み込むファイル数を制限（目安: 10-15ファイル以内）
2. **メモリ制約**: メモリ8GB制約がある場合は、さらに細分化（4-5ファイル/フェーズ）
   - 例: Phase 2、3、4を一度に依頼せず、Phase 2のみ → Phase 3のみ → Phase 4のみと分割
   - Phase 1を複数のサブフェーズ（Phase 1-1、1-2、1-3、1-4など）に細分化する
3. **機能的独立性**: 各フェーズが独立して動作確認可能な単位に分割

#### フェーズ分割の効果

- コンテキストウィンドウの節約（各フェーズで必要な情報のみロード）
- メモリ消費の抑制（大量のファイルを一度に処理しない）
- 問題の早期発見（小さい単位で動作確認）

#### 各フェーズ完了後の確認

- [ ] コード実装完了
- [ ] Code-Reviewerレビュー実施
- [ ] 動作確認（マイグレーション成功、テスト成功）
- [ ] 次フェーズへの影響確認

### 並列実行の活用

**メモリ・コンテキストに余裕がある場合は、独立したタスクを並列実行**

#### 並列実行可能なケース

- マイグレーション実行 + Code-Reviewerレビュー
- フロントエンドUI実装 + バックエンドAPI実装（仕様確定後）
- 複数の独立したモデルへの変更適用

#### 並列実行不可のケース

- 依存関係がある実装（A完了後にBを実装）
- メモリ制約がある場合（逐次実行を優先）
- コンテキストウィンドウが逼迫している場合

#### 実施例

```
# 並列実行例
1. japanese-coding-specialist: RLS設定マイグレーション実装
2. Code-Reviewer: Phase 1-2完了コードのレビュー（並列）
```

### Code-Reviewerの早期活用

**Phase完了直後にレビューを実施し、問題を早期発見**

#### レビュータイミング

- ✅ **Phase完了直後**: 次のPhaseに進む前に必ずレビュー
- ✅ **マイルストーン完了時**: 大きな区切りで包括的レビュー
- ❌ **全実装完了後**: 問題発見が遅れ、修正コストが増大

#### 検出可能な問題例

- nullable不整合（モデル定義とマイグレーションの不一致）
- インデックス重複定義
- 命名規則違反
- 外部キー制約の不整合
- セキュリティ上の懸念

#### 効果

- 次のPhaseへの影響を最小化
- 修正コストの削減（早期発見・早期修正）
- コード品質の向上

## Debuggerエージェント

### 使用タイミング

- **エラーログからのデバッグ**: エラーログやスタックトレースから問題を特定する際に使用
- **バグ調査**: 予期しない動作やバグの原因調査に使用

### 使用例

- エラーメッセージが表示される問題の調査
- ビルドエラー、実行時エラーの原因特定
- 意図しない動作の原因追跡

### タスク完了時

- project-orchestratorに調査結果と修正内容を報告する

## autonomous-testerエージェント

### 基本的な使用方法

- **テストの実施**: コード実装後のテスト実行に使用
- **包括的テスト**: 正常系・異常系・境界値テストを網羅的に実施
- **タスク完了時**: project-orchestratorにテスト結果を報告する

### 使用例

- 新機能実装後のテスト実行
- バグ修正後の回帰テスト
- リファクタリング後の動作確認

### テスト実装戦略

#### 各フェーズ完了後に自動テスト実施可能にする

- 毎回テスト実行する必要はないが、実装は必ず行う
- 自動テストがあることで、リグレッション検出が容易になる

#### テストファイル配置

- **バックエンド**: `backend/tests/unit/`, `backend/tests/integration/`
- **フロントエンド**: `frontend/src/__tests__/`

#### テストカバレッジ目標

- 主要機能は80%以上

#### テストタイプ

1. **単体テスト（unit）**: 各関数・クラスの動作確認
2. **統合テスト（integration）**: API・DB連携の動作確認
3. **E2Eテスト**: ユーザーシナリオの動作確認（必要に応じて）

#### テスト実行方針

- `npm test`を使用してワンショット実行（`vitest`単体は禁止）
  - 詳細は `~/.claude/tools/VITEST.md` を参照
- 実ユースケースでの動作確認を優先
- テスト結果とカバレッジを確認

## エージェント連携フロー

```
1. ユーザーからタスク受領
   ↓
2. project-orchestrator起動（タスク分解・計画）
   ↓
3. japanese-coding-specialist（Phase 1実装）
   ↓
4. Code-Reviewer（Phase 1レビュー）← 並列実行可能な場合あり
   ↓
5. autonomous-tester（Phase 1テスト）
   ↓
6. project-orchestratorに報告
   ↓
7. 次のPhaseへ（3に戻る）
```

**重要**: Debuggerは問題発生時のみ起動し、通常フローには含まれません。
