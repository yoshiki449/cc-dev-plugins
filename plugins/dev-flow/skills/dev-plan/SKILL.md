## 組織固有の QC 観点（overlay）

dev-flow は組織固有の品質観点を同梱しない。フェーズの開始時に overlay の適用状況を判定する。

```bash
bash <skill-dir>/../_shared/scripts/qc-overlay.sh --phase plan
```

- `overlay_applied` が `1` → `file` のパスを Read し、並んでいる観点をこのフェーズの追加レンズとして適用する
- `overlay_applied` が `0` → 観点を**自作せずスキップする**（組織の QC を dev-flow が発明してはいけない）

どちらの場合も **適用したかスキップしたかを1行報告する。黙って素通りしない。** `warnings` があれば添える。
判定が `overlay_present` ではなく `overlay_applied` を見ている理由を含む契約は
[../_shared/reference/qc-overlay.md](../_shared/reference/qc-overlay.md)。

要件定義書の確定前に判定し、適用できた観点は Issue 本文のレビュー観点に織り込む。

## 手順

> **フェーズ開始時の共通前処理**: `mkdir -p .agent && git branch --show-current > .agent/.dev-flow-active` を実行してフェーズマーカーを書き込む（suggest-dev-phase hook のフェーズ想起案内を沈黙させる。`/dev-ship` E7 が掃除する）

### A0. 新規 / 既存プロジェクトの判定

以下のファイル・ディレクトリを確認し、プロジェクトの種別を判定する。

**新規プロジェクトと判定する条件（複数満たす場合）:**
- `package.json`, `pyproject.toml`, `go.mod`, `Cargo.toml`, `pom.xml` 等のプロジェクトファイルが存在しない
- `docker-compose.yml` または `docker-compose.yaml` が存在しない
- `src/`, `app/`, `lib/` ディレクトリが存在しない、またはほぼ空
- `docs/` のみ存在する、あるいはリポジトリ直下にドキュメントファイルのみ

上記に該当しない場合は「既存プロジェクト」として扱い、A4（Dockerアーキテクチャ設計）をスキップする。

判定結果をユーザーに提示し、誤りがあれば修正を受け付ける。

### A1. 要件理解
1. ユーザーの要求を [要求の深掘り手順](../_shared/reference/requirement-elicitation.md) に従って深掘りし、要求カード（目的／現状の困りごと／成功を観察する条件／スコープ外／制約）を埋める
   - **曖昧さの検出**: 項目が空・程度を表す語だけ・対象が2通り以上に読める・解釈で実装が変わる、のどれかに当たる項目を質問で掘り下げる
   - **解決策の妥当性チェック**: 依頼が「○○を足して」のような手段の形なら、困りごとを先に聞き、その手段で困りごとが解消するかを確かめる
     <!-- requirement-elicitation:alternative -->
     - 解決策が困りごとを解消しないと判断したら、根拠（どの場面で何が残るか）を示して指摘し、元の案と代替案を並べて AskUserQuestion で選んでもらう
     - 元の案が選ばれたら、その判断を記録してそのまま進める
     - Claude が代替案で勝手に進めてはならない
     <!-- /requirement-elicitation:alternative -->
   - **質問順の原則**: 回答次第でアーキテクチャや技術選定が変わる質問（データ規模・同時利用者数・認証方式・既存システム連携・リアルタイム性の要否など）を優先して先に聞く。文言や画面の細部はその後で良い
   - **習熟度確認**: このドメイン・コードベースへのユーザーの習熟度（初見／触ったことがある／熟知）を1往復目の質問に含めて確認し、Issue 本文「背景・理由」と引継書に記録する（後段の説明粒度・確認頻度の調整に使う）
2. 既存コードベースを Explore エージェントで調査（コードを読めば分かることは、ユーザーに聞く前にここで調べる）
3. 法令・外部仕様がある場合は WebSearch で調査
4. DEVELOPMENT.md があれば読んでプロジェクト固有の規約を把握

### A1.5. ブラインドスポットパス

「知らないことを知らない」領域を計画の早期に明示化する。A1 のコードベース調査結果を踏まえて実施:

1. この計画が**触れていない領域・暗黙の前提・見落としがちな相互作用**を5件列挙する（例: 権限・既存バッチとの競合・キャッシュ・マイグレーション順序・タイムゾーン・同時編集・通知）
2. 各件を次の3つに振り分ける:
   - **調査する** → A2/A3 の調査項目に追加
   - **Open Questions に送る** → **A6 手順6 で1件ずつクローズする**（このバケツは経由地であって置き場ではない。未クローズのまま A7 へ進んではならない）
   - **無視してよい** → 理由を1行付けて記録
3. 振り分け結果を A6 設計レビューで提示し、引継書にも残す

### A1.8. 要求の確定 ⚠ スキップ不可

A1 で埋めた要求カードを、A2 以降の調査・設計に入る前に確定させる。A6 の設計レビューまで持ち越すと、要求の読み違いが仕様設計・画面設計を作り終えてから見つかり、設計ごと作り直しになるため。

1. 要求カードの5項目を復唱する（A1.5 で「Open Questions に送る」とした論点のうち、要求そのものに関わるものもここで閉じる）
2. 終了条件:
   <!-- requirement-elicitation:exit -->
   - 確定させる項目がすべて「埋まったとみなす条件」を満たしたら、項目を復唱してユーザーに合っているかを確認する。復唱の全文は AskUserQuestion のダイアログの中（question 文か選択肢の preview）に入れる。合意が取れたら終了し、修正が入ったら反映して再度復唱する
   - 依頼文と既存の資料だけで項目が埋まるなら、質問はせず復唱1回で終える
   - 3往復しても埋まらない項目は、「今ここで決める（決定内容を選択肢で提示）」か「承認済み保留（理由／いつ誰が決めるか／暫定案／影響範囲）」のどちらかで1件ずつ閉じる
   - 復唱への合意が取れるまで、また未クローズの項目が残っているうちは、次の手順へ進んではならない
   <!-- /requirement-elicitation:exit -->
3. 合意した要求カードは A7 で Issue 本文の「要求カード」セクションに、A9 で引継書に転記する

### A2. 技術スタック・依存パッケージ調査

新しいライブラリやパッケージの導入が必要な場合、以下を必ず実施する:

1. WebSearch で公式サイト・GitHub・npm を確認し、**最新の安定版バージョン**を特定
2. 以下の観点でチェック:
   - **EOL**: メンテナンス状況、最終リリース日、非推奨（deprecated）でないか
   - **セキュリティ**: 既知の脆弱性（CVE）、サプライチェーン攻撃の履歴、npm advisories
   - **保守性**: ダウンロード数の推移、コミュニティの活発さ、代替ライブラリの有無
3. バージョン指定は lockfile でピン留め。`^` や `~` を使う場合も lockfile の管理を徹底
4. サプライチェーン攻撃緩和: パッケージマネージャの「リリース直後を避ける」設定があれば有効化（例: npm の `min-release-age=7` を `.npmrc` に設定）
5. **参照実装の調査（任意）**: 望む挙動を既に実装している外部 OSS・他リポジトリがあれば WebSearch で特定する。有望なものは Explore エージェント（ローカルに clone 済みなら Read）で読解し、データモデル・アルゴリズム・エッジケース処理の要点を記録する。要点は A3 仕様設計の入力とし、Issue・引継書に「参照実装」として残す（ライセンスを確認し、コードのコピーはしない。設計の参考に留める）

### A3. 仕様設計
1. エンティティ設計（バックエンド: テーブル・API）
2. 既存パターンとの整合性確認

### A4. Dockerアーキテクチャ設計（新規プロジェクトのみ）

A0 で「新規プロジェクト」と判定した場合のみ実施する。

#### 設計方針
- 全サービスを1つの `docker-compose.yml` に集約する
- nginx をリバースプロキシとして配置し、外部公開ポートは `NGINX_PORT` の1つのみ
- 各サービスは Docker の内部ネットワーク（`app-network`）でのみ通信し、ホスト側へのポート露出を最小化する
- 環境変数は `.env` ファイルで管理し、`.env.example` をリポジトリにコミットする

#### サービス構成の設計手順
1. 要件からサービス一覧を洗い出す（例: frontend, backend, db, cache など）
2. 各サービスの役割・内部ポートを決定する
3. nginx のルーティング設定（`/api/` → backend, `/` → frontend 等）を設計する
4. ヘルスチェック設定（`depends_on` の `condition: service_healthy`）を設計する

#### plan 出力への記載（dev-setup が参照する）

引継書に以下のセクションを必ず含める:

```markdown
## アーキテクチャ設計

### Docker構成
- 全サービスを1つの docker-compose.yml に収める
- nginx リバースプロキシで単一ポート（NGINX_PORT）のみ外部公開
- 内部ネットワーク（app-network）でサービス間通信

### サービス構成
| サービス | 役割 | 内部ポート | ホスト公開 |
|---|---|---|---|
| nginx | リバースプロキシ | 80 | ${NGINX_PORT} |
| frontend | フロントエンド配信 | 3000 | なし（nginx経由） |
| backend | APIサーバー | 8000 | なし（nginx経由） |
| db | データベース | 5432 | なし |

### nginx ルーティング
| パス | 転送先 |
|---|---|
| /api/ | backend:8000 |
| / | frontend:3000 |

### 環境変数（.env）
| 変数名 | 説明 |
|---|---|
| NGINX_PORT | 外部公開ポート |
| DB_NAME | データベース名 |
| DB_USER | DBユーザー |
| DB_PASSWORD | DBパスワード（秘匿） |
```

※ 実際のサービス構成・ポート・ルーティングは要件に合わせて修正する。

### A5. 画面設計
1. **`dev-flow:ui-designer` エージェント**を起動
2. 要件・仕様を入力として渡す
3. 画面仕様を設計させる（以下を含む）:
   - 変更対象画面一覧
   - 画面遷移図（ASCII図）
   - 各画面の変更前/後ワイヤーフレーム（ASCII図）
   - 新規コンポーネントの Props・表示ロジック・データ取得仕様
   - 状態遷移図
   - 既存コンポーネント再利用マップ
   - エッジケース一覧
   - アクセシビリティ考慮事項
4. 画面仕様は **Issue 本文に直接記述する**（別ファイルの DESIGN.md は作成しない）

### A6. 設計レビュー
1. まず「レビューしてほしい判断」（変更可能性の高い順・最大5件。A7 で Issue 本文に転記する）を提示し、AskUserQuestion で1件ずつ「この判断のままで良いか／変更するか」を確認する
2. 仕様設計 + 画面仕様をユーザーに提示
3. 新規プロジェクトの場合は A4 の Docker アーキテクチャ設計もあわせて提示
4. AskUserQuestion でフィードバック収集
5. フィードバック反映（A1.5 ブラインドスポットパスの振り分け結果もここで提示する）
6. **未確定事項のクローズ ⚠ スキップ不可**: A1.5 で「Open Questions に送る」と振り分けた論点、および A1〜A5 で解釈が2通り以上ありえた要件を、**1件ずつ AskUserQuestion で閉じる**。選択肢は原則この3つ:
   - **今ここで決める** → 決定内容そのものを選択肢として提示する（「どうしますか？」と自由回答で投げない）
   - **調査してから決める** → A2/A3 の調査項目に戻す（保留にはしない。調査後にこの手順へ戻る）
   - **承認済み保留にする** → 「保留の理由 / いつ誰が決めるか / それまでの暫定案 / 決定が変わったときの影響範囲」の4点を提示して**保留すること自体の承認**を取る

   **1件でも未クローズのまま A7 へ進んではならない。** 合意した解釈は仕様本文に断定形で書き直す（「〜と解釈する」ではなく「〜する」）。承認済み保留が3件以上出るなら計画がまだ立っていないサインなので A2/A3 の調査に戻る。

### A7. Issue 作成

[reference/issue-template.md](reference/issue-template.md) のテンプレートに従って Issue 本文を組み立て、`gh issue create --body-file -` で投稿する。

- 必ず含めるセクション・省略可能なセクション・記述ルールはすべて reference 側に定義
- ヒアリング結果から「省略可能」と判断した項目は理由を引継書に残す
- **投稿前チェック（必須）**: 本文を「未確定 / TBD / 要検討 / 後で決める / 適宜 / 場合による / 必要に応じて」で1回検索する（例: `grep -nE '未確定|TBD|要検討|後で決める|適宜|場合による|必要に応じて' <本文ファイル>`）。「未解決事項（承認済み保留）」セクション外にヒットしたら、それが**実際に未確定を残した記述**か、**語そのものへの言及**（規約の引用・過去の経緯説明）かを1件ずつ判定し、前者が1件でもあれば投稿せず A6 手順6 に戻る。「言及だから」で流す判定を2件以上続けたら、それは自分に都合よく読んでいるサインなのでユーザーに確認する

### A8. フェーズ分割
1. コンテキストウィンドウを考慮して Phase 分割（10-15 ファイル/Phase）
2. バックエンド → フロントエンド の順
3. 各 Phase の依存関係を明示
4. 新規プロジェクトの場合、最初の Phase に「Docker 基盤構築」を含める

### A8.5. 採用プランの docs/plans/ 取り込み（Plan mode 利用時）

企画にあたって Plan mode のプランファイル（`~/.claude/plans/<ランダム名>.md`）を承認・採用した場合、**プランをプロジェクトに取り込む**（ドキュメント保管規約）:

1. `mkdir -p docs/plans`
2. `cp ~/.claude/plans/<ランダム名>.md docs/plans/YYYY-MM-DD-<トピック>.md`（日付＋内容が分かるトピック名にリネーム）
3. git に追加（Issue コミットに同梱可）: `docs: 採用プランを docs/plans/ に取り込み`
4. **実行マニフェスト**（dev-hub の実行履歴ビュー用）に記録する:
   ```bash
   node skills/_shared/scripts/hub-run-add.mjs --repo <repoルート> \
     --run issue-<Issue番号> --label "<機能名>" --flow dev-plan --issue <Issue番号> \
     docs/plans/YYYY-MM-DD-<トピック>.md
   ```
   （以降のフェーズ［auto-build / dev-ship 等］が同じ run-id に成果物を追記していくことで、1開発サイクルの成果物が dev-hub で1セクションにまとまる）

Plan mode を使っていない場合はスキップ。

### A9. 引継書作成 ⚠ 必須（スキップ不可）

> **注意**: このステップは plan フェーズの最終ステップであり、**ユーザーとのやり取りが途中で入っても必ず実行すること**。Issue 作成後にユーザーからフィードバックがあった場合も、フィードバック反映後に引継書を作成してからフェーズを完了とする。

1. 引継書ファイルパスを発番:
   ```bash
   NEW=$(bash skills/_shared/scripts/new-handover-path.sh <Issue番号>)
   ```
2. [../_shared/reference/handover-template.md](../_shared/reference/handover-template.md) の共通骨格 + plan フェーズ固有セクション（Issue URL、要求カード、フェーズ分割、（新規時）アーキテクチャ設計、**画面デザインフェーズ判定**）を組み合わせて `$NEW` に書き出す
   - 共通骨格の「未解決事項（承認済み保留）」には Issue 本文と同じ内容を転記する。0 件なら「なし」と明記する（欄ごと省略しない。空欄は「確認していない」と区別がつかないため）
3. 次フェーズを以下のロジックで案内する:
   - 新規UIを伴う場合（A5 で画面一覧が複数生成された、または既存コンポーネント再利用のみではない場合）→ 「/clear して `/dev-design` に進めますか？」
   - UIなし・既存UI再利用のみの場合 → 「/clear して `/dev-setup` に進めますか？」（design はスキップ）

#### plan 引継書のフェーズ固有セクション（design 判定）

引継書に以下のブロックを必ず含める。`/dev-design` および `/dev` ルーターが次フェーズ判定に使う:

```markdown
## 画面デザインフェーズ判定
- 新規UI有無: <あり | なし>
- design フェーズ推奨: <yes | no>
- 判断理由: <例: A5 で 5 画面の新規ワイヤーフレームを生成したため | サーバ側のみの変更のため | 既存コンポーネント再利用のみのため>
- 対象画面（design に渡す候補）:
  - <画面1>
  - <画面2>
```

## 出力物
- GitHub Issue（reference/issue-template.md 準拠）
- `.agent/handover-YYYYMMDD-HHMM-issue<番号>.md`（引継書）
  - 新規プロジェクトの場合: 引継書にアーキテクチャ設計セクションを含める（dev-setup がこれを読んで Docker 構成をスキャフォールドする）

## dev-setup との連携（新規プロジェクト時）

引継書の `## アーキテクチャ設計` セクションを dev-setup が読み込み、以下を自動生成する:
- `docker-compose.yml`（全サービス定義）
- `nginx/nginx.conf`（リバースプロキシ設定）
- `.env.example`（環境変数テンプレート）
