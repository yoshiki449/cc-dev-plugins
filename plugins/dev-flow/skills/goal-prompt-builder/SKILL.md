description: dev-flow形式のGitHub Issue（要求カード・未解決事項・実装状況チェックリストを含む）から、Claude Codeの`/goal`コマンドに渡す完了条件文（測定可能な終了状態・検証方法・制約・ターン上限を含む）を組み立てる。ユーザーが「Issue #Nをgoalコマンドで進めたい」「クラウドで/goalを使ってこのIssueを完走させたい」「goalの条件文を作って」のように、特定のIssueを/goalで自動継続させたいと明示したときに必ず使う。単に「クラウドで実装して」「自動で進めて」とだけ言われた場合（/goal自体への言及がない場合）には使わない——その場合はdev-flowの通常フェーズコマンド案内に任せる。

## このスキルがすること・しないこと

- **する**: 指定されたGitHub Issueの本文を読み、`/goal`にそのまま貼り付けられる条件文を作る。改行を使って人間が読みやすい形にしてよい（1行に詰め込む必要はない）
- **しない**: Issueの作成・要件定義・実際のコード実装・クラウド環境のセットアップ案内（Setup script等）・`/goal`の実行そのもの。これらは`dev-flow:dev-plan`や`dev-flow:cloud-env-setup`、`dev-flow:dev-implement`等の既存フローに委ねる

出力は条件文のみ。実行手順の解説は付けない（別途聞かれたときに答える）。

## `/goal`条件文の作り方の背景

`/goal`は、ターンが終わるたびに評価モデル（既定Haiku）が**会話のトランスクリプトだけ**を読んで条件の達成を判定する仕組み。evaluatorは自分でコマンドを実行したりファイルを読んだりしないので、条件は「Claude自身の出力（発言・貼り付けたログ）として証拠が残る形」で書く必要がある（公式ドキュメント: https://code.claude.com/docs/en/goal）。

良い条件文は次の4要素を持つ。

1. **測定可能な終了状態**（1つ）: テスト結果、ビルドexit code、PRの存在、など
2. **検証方法**: Claudeが何を実行してどう示すか（例:「`npm test`がexit 0で終わる」）
3. **制約**: 途中で変えてはいけないもの（他Issueが触れるファイル・マージ禁止・使えないツール等）
4. **ターン上限**: 「または30ターンで停止する」のような一文

## 手順

### 1. 対象Issueを特定する

Issue番号とリポジトリ（`owner/repo`形式）を確認する。ユーザーの発話に無ければ聞く。

### 2. Issue本文を読む

```bash
gh issue view <番号> --repo <owner/repo> --json title,body,url
```

dev-flow形式のIssueなら、本文に以下のセクションがあるはずなので、それぞれを条件文の材料として抜き出す。

| Issue本文のセクション | 条件文への反映先 |
|---|---|
| 要求カード「成功を観察する条件」 | 測定可能な終了状態 |
| 実装状況（チェックリスト） | 終了状態の具体化・検証方法（「チェックリスト全項目完了」） |
| 未解決事項（承認済み保留） | 制約（「実装中に自分で検証し、暫定案にフォールバックする」という、人間の判断待ちにしない指示に変換する） |
| 要求カード「スコープ外」 | 制約 |
| レビューしてほしい判断 | 制約（選ばれた案から逸脱しないこと） |

dev-flow形式でないIssue（セクションが揃っていない）の場合は、本文とタイトルから同じ4要素を推測して組み立てる。推測した旨と、確認してほしい点をユーザーに一言添える。

### 3. 同リポジトリの他のopen Issueとのファイル重複を確認する

```bash
gh issue list --repo <owner/repo> --state open --json number,title,body
```

本文中に今回のIssueと同じファイルパス・同じディレクトリへの言及がある他のIssueがあれば、「Issue #Mが対象とする〈ファイル/ディレクトリ〉には触れない」という制約を追加する。無ければこの制約は省略する（見つからないものを無理に書かない）。

### 4. テストコマンドを検出する

リポジトリの`package.json`（`scripts.test`）／`pyproject.toml`／`go.mod`等から実際のテストコマンドを検出し、検証方法に使う。分からなければIssue本文やリポジトリのCLAUDE.mdのコマンド一覧を確認する。**推測でコマンド名を書かない**（存在しないコマンドを検証方法にすると、evaluatorがどう判定してよいか分からずゴールが停滞する）。

### 5. クラウド環境固有の制約を確認する

「このクラウド環境で使えないMCPツールやサービスはあるか」をユーザーに確認する（ai-memory MCP・社内SaaS認証等、環境ごとに違うため毎回確認が必要）。無ければこの制約は省略する。

### 6. ターン上限を見積もる

実装状況チェックリストの項目数・変更予定ファイル数から目安を立てる。チェックリスト5項目以下・変更ファイル数が少ない小規模タスクなら20ターン程度、それより大きければ30〜40ターン程度を目安にする。迷ったら聞き返すより、Issueの規模から妥当な数値を出して提示する（違っていればユーザーが直せる）。

### 7. 条件文を組み立てて出力する

4要素を`/goal <条件文>`の形でコードブロックとして出力する。1行に詰め込む必要はない——箇条書きや改行を使い、人間が読んで内容を追える形にする。4000字を超えていないか文字数を数えて確認してから出す（改行文字も文字数に含めて数える）。

## 例

Issue本文に「要求カード: 成功を観察する条件＝XがYを返す」「実装状況: [ ] a.ts / [ ] b.ts」「未解決事項: `${CLAUDE_PLUGIN_ROOT}`が使えるか未検証、実装中に検証してフォールバック」とあった場合:

```
/goal 以下がすべて満たされたら完了とする。

終了状態: Issue #1（https://github.com/owner/repo/issues/1）の実装が完了し、mainへのマージ前のPRが作成されていること。

検証方法:
- `npm test` がexit 0で終わること
- Issue #1本文の「実装状況」チェックリスト全項目が完了していること
- `gh pr list --repo owner/repo --state open` で対象PRが確認できること

制約:
- mainへのマージは行わない（PR作成まで）
- `${CLAUDE_PLUGIN_ROOT}`変数が使えるかは実装中に自分で検証し、使えなければ絶対パス解決にフォールバックする（人間の判断を待たない）

または25ターンで停止する。
```
