# /dev-fix - 修正フェーズ

## 概要

`/dev-verify` で動作確認後、ユーザーから修正希望が出た場合に使用するフェーズ。
Issue仕様との差異分析を起点に、修正方針の策定→実装→検証まで一連で行う。

**繰り返し実行可能**: 修正希望が複数回出る場合は、都度 `/dev-fix` を実行する。

## 手順

> **フェーズ開始時の共通前処理**: `mkdir -p .agent && git branch --show-current > .agent/.dev-flow-active` を実行してフェーズマーカーを書き込む（suggest-dev-phase hook のフェーズ想起案内を沈黙させる。`/dev-ship` E7 が掃除する）

### F0. 引継書の読み込み
1. `.agent/handover-*.md` の最新ファイル（`ls -1 .agent/handover-*.md | tail -1`）を読み込む
2. 現在のブランチ、実装済み機能、環境情報を確認
3. 引継書に記録された **worktree 絶対パス** を控える（F0.5 で照合）

### F0.5. worktree 検証 ⚠ 必須（スキップ不可・中断条件あり）

> **原則**: **worktree の中でしか修正コミットを作らない**。main clone やベースブランチ（main/master/develop 等）上で Edit/Write/コミットする前に必ずここで止める。過去に main 誤コミット事故が発生している（memory `bash-cwd-drift-in-worktree`）。

1. `pwd` と `git branch --show-current` で現在地を実測する（ターンをまたいだ直後は特に）
2. `bash skills/_shared/scripts/ensure-worktree.sh` を実行し、status を確認する:

| status | 挙動 |
|---|---|
| `ok` | そのまま F1 に進む |
| `non_worktree_path` | worktree 内だが規約外パス。ユーザーに一言報告してそのまま F1 に進む（動作はする） |
| `on_main_branch` / `flat_repo` | **中断**。ユーザーに以下を伝える: 「ベースブランチ（main/master/develop 等）直上 or worktree 未作成のため修正できません。`/dev-setup` を実行して worktree を作成してから戻ってきてください。既に worktree が別ディレクトリにあれば絶対パスを教えてください（そこに cd してから再度 `/dev-fix`）」 |
| `not_a_repo` | 中断。ユーザーに repo 位置を確認 |

3. 引継書に worktree 絶対パスが記録されているなら、`git rev-parse --show-toplevel` の結果と一致するかを照合する。ズレていれば **どちらが正しいかユーザーに確認するまで修正コミットを作らない**

### F1. 修正希望の整理

ユーザーからの修正希望を構造化する:

1. **修正希望の一覧化**: ユーザーの指摘を箇条書きに整理
2. **分類**: 各指摘を以下に分類
   - **仕様不一致**: Issue/DESIGN.mdの仕様と実装が異なる
   - **仕様追加**: Issueに記載のない新しい要望
   - **UI改善**: 見た目・操作感の改善要望
   - **バグ**: 意図しない動作
   - **テスト修復**: 失敗テスト・flaky・skipped の解消
   - **テスト漏れ**: `/dev-test-ledger` の🔴（テスト漏れ）や QA レポートで見つかった、自動テスト向きの未検証項目を追加する
   - **履歴整理**: PR 分割・コミット整理・コンフリクト解消
3. **深掘り**: [要求の深掘り手順](../_shared/reference/requirement-elicitation.md) に従い、分類ごとに次の項目を確定させる。項目が曖昧（空・程度を表す語だけ・対象が2通り以上に読める・解釈で修正内容が変わる）なら質問で掘り下げる。Issue に書いてあることは聞かずに F2 の要領で先に Issue を読む

   <!-- dev-fix:elicitation-items -->
   | 分類 | 確定させる項目 | 解決策の妥当性チェック |
   |---|---|---|
   | 仕様追加・UI改善 | 目的・現状の困りごと・成功を観察する条件（スコープ外・制約は Issue 側にあるので聞かない） | する |
   | バグ・仕様不一致 | 再現手順・期待する結果・実際の結果（期待する結果が Issue に書かれていれば聞かない） | 「○○で直して」と手段つきで依頼されたときにする |
   | テスト修復 | 正しいのはテストの期待値か実装か | skip・リトライ・待ち時間延長・期待値の書き換えを選ぶ前にする |
   | 履歴整理 | 分け方の基準（レビュー単位かリリース単位か）。両側が挙動を変えているコンフリクトは、どちらの挙動を残すか | しない |
   <!-- /dev-fix:elicitation-items -->

   テスト修復で「正しいのはテストの期待値か実装か」を決めずに直すと、テストを実装に合わせて緑にするだけになり、テストが守っていた仕様が黙って消える。

   **テスト漏れは上表の深掘りを行わない。** `/dev-test-ledger` の🔴行や QA レポートには「何が検証されていないか」「テスト層」が既に書かれており、これ自体が確定済みの要求だからである。F2 以降へそのまま進める。

   解決策の妥当性チェックをする分類では、依頼された手段で困りごと（バグ・テスト修復では症状の原因）が解消するかを確かめる:
   <!-- requirement-elicitation:alternative -->
   - 解決策が困りごとを解消しないと判断したら、根拠（どの場面で何が残るか）を示して指摘し、元の案と代替案を並べて AskUserQuestion で選んでもらう
   - 元の案が選ばれたら、その判断を記録してそのまま進める
   - Claude が代替案で勝手に進めてはならない
   <!-- /requirement-elicitation:alternative -->

   終了条件:
   <!-- requirement-elicitation:exit -->
   - 確定させる項目がすべて「埋まったとみなす条件」を満たしたら、項目を復唱してユーザーに合っているかを確認する。復唱の全文は AskUserQuestion のダイアログの中（question 文か選択肢の preview）に入れる。合意が取れたら終了し、修正が入ったら反映して再度復唱する
   - 依頼文と既存の資料だけで項目が埋まるなら、質問はせず復唱1回で終える
   - 3往復しても埋まらない項目は、「今ここで決める（決定内容を選択肢で提示）」か「承認済み保留（理由／いつ誰が決めるか／暫定案／影響範囲）」のどちらかで1件ずつ閉じる
   - 復唱への合意が取れるまで、また未クローズの項目が残っているうちは、次の手順へ進んではならない
   <!-- /requirement-elicitation:exit -->

### F2. Issue仕様との比較

1. GitHub Issue（`gh issue view <番号>`）を取得
2. DESIGN.md があれば読み込む
3. 各修正希望について仕様との照合:
   - **仕様に記載あり** → 実装漏れ or 実装不備。修正必須
   - **仕様に記載なし** → ユーザーに確認:
     - 今回のスコープに含めるか
     - Issueに追記するか（含める場合）
     - 別Issueとして切り出すか（今回は対応しない場合）
4. スコープ判断の結果をユーザーに報告

### F3. 修正方針の作成

スコープ内の修正について方針を策定:

1. **影響範囲の特定**: 修正対象ファイルを洗い出す
2. **denylist 照合**: `.agent/loop-denylist.txt` があれば読み込み、修正対象ファイルと照合する。抵触するファイルがある場合は方針提示時に「このパスは自動編集禁止（denylist）。手動対応 or denylist 見直しが必要」と明示的に報告する（黙って対象から外さない）
3. **修正方針の策定**: 各修正項目について
   - 変更するファイルとその内容の概要
   - 既存テストへの影響
   - 新規テストの要否
4. **優先順位**: 仕様不一致 > バグ > テスト修復 > UI改善 > 仕様追加 の順（履歴整理は他の修正がすべて終わってから行う）
5. **方針をユーザーに提示し、承認を得る**

### F4. ソースコードの修正

承認された方針に基づき修正を実行する。作業範囲（[スコープ規律](../_shared/reference/scope-discipline.md)）:

<!-- scope-discipline -->
- 頼まれた範囲で仕上げる。曖昧な点は注意深い同僚のように解釈し、読み方によって作業が大きく変わるときだけ確認する
- より良い方法があると判断したら一文で伝え、依頼どおりに進める。範囲を黙って広げも狭めもしない
- 終わっていない部分があれば完了と言わず、終えた部分と、残りとその理由を書く
<!-- /scope-discipline -->

手順:

1. **テストの更新**（変更がある場合）:
   - **分類がテスト漏れ かつ テスト層が「運用」**: `dev-flow:e2e-test-generator` エージェントを起動し、対象のユーザーストーリー/機能テストを生成させる。この項目は `/dev-test-ledger` の🔴（テスト漏れ）または QA レポートで既に「穴」と確定している既知のギャップなので、e2e-test-generator 手順6・7の既定の生成可否判定（コア導線変更 or ユニット不可、の2条件）は適用しない——その要否判断は呼び出し側（台帳・QA）で既に済んでいる。生成後はエージェントにコミットまで行わせる（`test:` プレフィックス）
   - **分類がテスト漏れ かつ テスト層がそれ以外（機能等）**: ユニット/API テストとして下記と同じ手順で追加する
   - **それ以外の分類でテスト変更が必要な場合**: 既存テストの期待値を修正・新規テストを追加し、テスト実行で修正前のFAILを確認（TDDのRED）
2. **ソースコードの修正**（テスト漏れ・分類=運用の場合は e2e-test-generator が完結させるため本ステップは不要）:
   - 方針に沿って実装
   - 修正ごとにlint実行
   - F3 で承認された方針から逸脱した判断や想定外のエッジケース対応をした場合は、その場で `.agent/deviations-wip.md` に1行追記して続行（F6 の引継書に転記して削除。`/dev-loop` 経由の場合は dev-loop の進捗ファイル `## Deviations` に追記）
3. **テスト実行**: 全テストPASSを確認
4. **コミット**: 修正内容に応じたプレフィックス
   - 仕様不一致・バグ: `fix: <内容> #<Issue番号>`
   - UI改善: `style: <内容> #<Issue番号>`
   - 仕様追加: `feat: <内容> #<Issue番号>`
   - テスト修復: F1 で「テストが正しい」と確定したなら実装の修正なので `fix:`、「実装が正しい」と確定したなら `test:`

### F5. 動作検証

1. ローカル環境で修正箇所の動作確認
2. chrome-devtools MCPでブラウザ操作（利用可能な場合）
3. 修正希望が解消されたかをユーザーに確認
4. E2Eテストがあれば再実行

### F6. 結果報告と引継書更新

#### ユーザーへの報告

```
## 修正結果

| # | 修正希望 | 分類 | 対応 | 状態 |
|---|---------|------|------|------|
| 1 | ○○の表示が仕様と異なる | 仕様不一致 | 修正済み | DONE |
| 2 | △△を追加してほしい | 仕様追加 | 別Issue #XX | SKIP |
| 3 | □□ボタンの位置を変更 | UI改善 | 修正済み | DONE |
```

#### 引継書の作成 ⚠ 必須（スキップ不可）

> **注意**: このステップはfixフェーズの最終ステップであり、**ユーザーとのやり取りが途中で入っても必ず実行すること**。

`.agent/handover-YYYYMMDD-HHMM[-issue{番号}].md` として引継書を**新規作成**:
- 修正した内容と対応コミット
- スコープ外として別Issueに切り出した項目
- 未解決の指摘（あれば）
- Deviations（`.agent/deviations-wip.md` を転記して削除。無ければ「逸脱なし」と1行）
- 次のアクション提案:
  - 追加修正あり → 「再度 `/dev-fix` を実行してください」
  - 修正完了（QA未実施） → 「`/clear` してQAフェーズ（`/dev-qa`）に進めますか？」
  - 修正完了（QA指摘の修正） → 「`/clear` して再QA（`/dev-qa`）に進めますか？」（再探索は指摘箇所周辺に絞ってよい）
  - 修正完了（QA合格済み） → 「`/clear` して `/dev-test-ledger`（統合）でテストカバレッジを確認してから `/dev-ship` に進めますか？」（テストを修正した場合は台帳が変わるため）

## コミット粒度ルール

| 分類 | プレフィックス | 例 |
|------|-------------|---|
| 仕様不一致の修正 | `fix:` | `fix: 一覧画面のソート順を仕様通りに修正 #123` |
| バグ修正 | `fix:` | `fix: 保存ボタン連打で重複登録される問題を修正 #123` |
| UI改善 | `style:` | `style: モーダルの幅をDESIGN.mdに合わせて調整 #123` |
| 仕様追加 | `feat:` | `feat: 一覧画面にCSVエクスポート機能を追加 #123` |
| テスト修正 | `test:` | `test: 修正に合わせてE2Eテストを更新 #123` |
| テスト修復（実装が正しいと確定） | `test:` | `test: 並び順の期待値を仕様どおりの降順に直す #123` |
| テスト修復（テストが正しいと確定） | `fix:` | `fix: 一覧の並び順がテストの期待する降順になっていなかった問題を修正 #123` |
| テスト漏れ（テスト層=運用） | `test:` | `test: 申請一覧の並び替え導線のE2Eテストを追加 #123` |
| テスト漏れ（テスト層=運用以外） | `test:` | `test: ニックネーム空欄保存時のバリデーションテストを追加 #123` |
