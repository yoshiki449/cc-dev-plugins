# サブエージェント成果物の受け渡し契約

サブエージェントを並列起動して成果物を集める全スキル（dev-self-review / dev-qa / dev-test-ledger / dev-implement）が従う共通規約。

## 前提

**完了通知は成果物の完成ではない。** エージェントは調査を終えた時点で応答を返すことがあり、指示された Write を実行しないまま完了扱いになる。tools に `Write` があっても起きる（実測で5体中4体が Write 権限つきで書かずに終了した）。

## エージェントは2つの型に分かれる

| 型 | 該当 | 成果物の渡り方 |
|---|---|---|
| **ファイル出力型** | convention-reviewer / simplify-reviewer / requirement-coverage-checker / codex-cross-reviewer / Code-Reviewer / test-ledger-writer / adversarial-verifier | 指定パスへ `Write` |
| **本文返却型** | qa-goal-evaluator / qa-technical-evaluator / qa-ux-evaluator （および QC overlay の `reviewer_agent`） | 最終メッセージ本文。呼び出し側が逐語保存する |

本文返却型が `Write` を持たないのは設計であって不具合ではない。ハーネスは `agentId` を持つ実行から `^(REPORT|SUMMARY|FINDINGS|ANALYSIS).*\.md$` への書き込みを拒否する（ハーネスの該当関数を読んで確認済み。設定で外す口は無い）。**改名で回避しない。**

## 起動プロンプトに必ず含める（ファイル出力型）

出力先パスを渡すだけでは足りない。次の4項目を**初回から**入れる。順序も含めて意味がある。

<!-- subagent-output-contract:file-output -->
1. 調査に使ってよいツール呼び出しは **N 回まで**（呼び出し側が数値を入れる。**ハーネスのターン上限より小さい値にする**）。N 回に達したら調査を止める
2. 調査が不完全でも、必ず最後に Write ツールで指定パスへ出力する
3. Write が完了してから最終応答を返す。本文返却だけで終えるのは失敗とみなす
4. 指摘が0件なら「0件」と明記したレポートを Write する
<!-- /subagent-output-contract:file-output -->

**N はハーネスのターン上限より小さくする。** 同値だと書く余地が残らない。2026-09-01 の実測では、ハーネス上限が20のときに N=20 を指定したエージェントが**20回を使い切って未出力のまま停止**した。「残り5回になったら Write に入る」と添えても効かない（エージェントは自分が何回使ったかを正確に数えられない）。上限の6割程度を目安にする（20 なら 12）。

同じ日に N=20 を渡した別のエージェントが14回で完走したが、これは調査が早く終わっただけで、契約が効いた証拠ではない。**完走した事実を「N=20 で足りる」の根拠にしない。**

**1 で回数を数値にするのが要点。**「打ち切ってよい」という許可では足りない。打ち切る判断をエージェント自身に委ねると、上限に当たるまで調査を続けて書く機会が来ない。2026-09-01 の実測では、この4項目を先頭に置いてもなお **5体中3体がターン上限に達して未出力のまま停止**した（うち1体は「これからレポートを書きます」と述べた直後）。

4 が無いと、指摘なしのエージェントが「書くものが無い」と判断してファイルを作らず、呼び出し側からは失敗と区別できない。

## 起動プロンプトに必ず含める（本文返却型）

`Write` を持たないエージェントには上の4項目が当てはまらない。成果物は最終メッセージ本文そのものなので、2 と 3 を置き換える。

<!-- subagent-output-contract:body-return -->
1. 調査に使ってよいツール呼び出しは **N 回まで**（呼び出し側が数値を入れる。**ハーネスのターン上限より小さい値にする**）。N 回に達したら調査を止める
2. 調査が不完全でも、必ず所見を最終メッセージ本文で全文返す
3. 完了通知だけで終えるのは失敗とみなす。本文そのものが成果物
4. 指摘が0件なら「0件」と明記して返す
<!-- /subagent-output-contract:body-return -->

1 と 4 はファイル出力型と同じ。**型を取り違えて「Write せよ」と書くと、書けないエージェントに不可能な指示を出すことになる**（そのエージェントは Write を試して失敗するか、指示を無視して本文だけ返す。どちらも呼び出し側からは同じに見える）。

## 呼び出し側の義務

消費側の SKILL.md には、型に応じた次の2行を**そのまま**置く。起動プロンプトの4項目と同じく複製で配り、`subagent-output-contract.test.js` が byte-identical を検査する。

**なぜ完全一致で配るのか**: 以前は「出力確認（スキップ不可）」のような語を消費側から `includes()` で探していたが、**その直後に否定を足すだけで検査を通り抜けられた**（`…差し替える必要はない。同じプロンプトのまま再起動する` で 9/9 PASS。2026-09-01 に codex が実測）。部分一致では極性の反転を防げない。

**ファイル出力型の消費者に置く2行**

<!-- subagent-output-contract:file-output-checks -->
- **出力確認（スキップ不可）**: 起動した本数分の実体を確認する。「上限に達して停止した」通知も完了として届くので、通知の種類で判断しない
- **再起動するときはプロンプトを差し替える（スキップ不可）**: 同じプロンプトで投げ直せば同じ結果になる。4項目を先頭に置き、残りツール呼び出し回数を明示し、既に得られている指摘を渡す
<!-- /subagent-output-contract:file-output-checks -->

**本文返却型の消費者に置く2行**

<!-- subagent-output-contract:body-return-checks -->
- **本文を要求する（既定手順・スキップ不可）**: 起動しただけで本文が届くことを前提にしない。「並列起動 → 各エージェントへ本文を要求 → 逐語保存」の3ステップを踏む
- **保存確認（スキップ不可）**: 逐語保存した本数分の実体を確認する。「上限に達して停止した」通知も完了として届くので、通知の種類で判断しない
<!-- /subagent-output-contract:body-return-checks -->

この2行の下に、スキル固有の具体手順（対象パス・本数の数え方）を続けて書く。

### 1. 存在確認（スキップ不可）

完了通知を受けたら、統合へ進む前に実体を確認する。**「上限に達して停止した」という通知も `completed` として届く**ので、通知の種類で区別せず必ず実体を見る。

```bash
test -s <出力先パス> || echo "MISSING: <エージェント名>"
```

起動しなかったエージェントのファイルが無いのは欠落ではない。**起動した本数分**が揃っているかを見る。

### 2. 欠けていたら、同じプロンプトで再起動しない

同じ入力を投げれば同じ結果になる。次の3点を差し替えた別プロンプトで再起動する。

- 上の4項目を先頭に置く（付け足しではなく先頭）
- 調査の試行回数・時間の上限を明示する
- 既知の指摘を渡し、「これ以外を探すことに時間を使う」と指示する（重複調査を削る）

2026-09-01 に上限で停止した3体へこの差し替えを行い、**全員が1〜2ツール呼び出しで成果物を出した**。差し替えた文面は「追加調査は一切しない」「次のツール呼び出しで Write する」「残りは N 回以内」の3点で、いずれも初回プロンプトより強い言い方にしてある。

### 3. 本文返却型では、本文の再要求を既定手順として書く

起動しただけで本文が届くことを前提にしない。実測では**4体中4体**が idle 通知のみを返し、`SendMessage` で「所見の全文を最終メッセージ本文として返してください」と再要求して初めて返した。手順は「並列起動 → 各エージェントへ本文を要求 → 逐語保存」の3ステップで書く。

逐語保存とは、返答本文をそのまま保存することを指す。要約・並べ替え・重要度の再判定をしない。

### 4. 未返却を「指摘0件」と解釈しない

これが最も損害が大きい誤読になる。2026-08-17 の実測では、4体の未出力を0件と読んでいれば Critical 2件（帳票のニックネーム実装漏れ）を見逃したまま PR を出していた。再起動しても返らない場合は、呼び出し側が代行評価するか、その観点が欠落していることを成果物に明記して先へ進む。

## 検証

このスキルを改修したら、実プロジェクトで1回フルパス実行し、起動した本数分のファイルが揃うことを `ls` で確認する。エージェントの挙動は SKILL.md を読むだけでは分からない。
