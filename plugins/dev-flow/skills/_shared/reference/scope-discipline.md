# スコープ規律（scope-discipline）

実装・修正を進めるメインセッションが、頼まれた範囲の中で仕上げるための一文。`dev-implement` / `dev-fix` / `dev-loop` が使う。

## なぜ置くか

Claude Opus 5 は、頼まれていない手順を足したり、タスクの中身を自分の判断で組み替えたりすることがある。Anthropic の移行ガイドでは、下の文と同じ趣旨の指示で範囲の変更がほぼ無くなり、確認の質問も増えなかったと報告されている。サブエージェントの `implementer` は「最小実装・ついで禁止」を持つが、メインセッションが実装・修正を進める経路はこの指示を持たないので、ここで与える。

Sonnet や Codex で実行する場合にも害は無い（範囲を守ることはモデルによらず求める挙動）。

## 正準の文

消費側の SKILL.md はマーカーの中を同じ文で持つ（`scripts/scope-discipline.test.js` が照合する）。

<!-- scope-discipline -->
- 頼まれた範囲で仕上げる。曖昧な点は注意深い同僚のように解釈し、読み方によって作業が大きく変わるときだけ確認する
- より良い方法があると判断したら一文で伝え、依頼どおりに進める。範囲を黙って広げも狭めもしない
- 終わっていない部分があれば完了と言わず、終えた部分と、残りとその理由を書く
<!-- /scope-discipline -->

## 例外: 仕様に無い、ユーザーに見える挙動

上の一文の「曖昧な点は解釈する」は、頼まれていない手順を足す・範囲を組み替えることを抑えるためのもので、範囲そのものの話である。一方、運用では「仕様に書かれていない文言・失敗時の挙動・並び順などを、実装の段階で AI が解釈して決めていて、意図とずれた」ことが報告されている。「読み方によって作業が大きく変わるときだけ確認する」では、文言や並び順のように作業量が変わらない細部は確認の対象から漏れる。

そこで、ユーザーに見える挙動に限って例外を置く。範囲規律の一文は変えない。例外は範囲の外の話なので、確認が増えるのは、仕様に無いユーザーに見える判断が出たときだけになる。

`dev-implement` と `dev-fix` は、その場で止めて聞く（`scope-discipline-gap`）。`dev-loop` は途中で止まらない設計（唯一の停止点は境界確認）なので、暫定案で進めて記録し、境界確認で必ず提示する（`scope-discipline-gap-loop`）。

<!-- scope-discipline-gap -->
- 仕様（Issue・DESIGN・引継書）に書かれていない判断のうち、ユーザーに見える挙動（画面の文言・表示・エラー時の挙動・並び順・権限・データの残り方・削除の可否）に関わるものは、上の「曖昧な点は解釈する」の対象外。解釈して進めず、その場で止めて AskUserQuestion で聞く。この行は上の一文より優先する
- 質問には推奨案と根拠を付ける（書式は要求の深掘り手順の「問いの書式」）。決まった内容は Deviations に「ユーザー確認済み」と書く
- ユーザーに見えない内部の判断（名前・内部の分割・既存パターンに沿った選び方）は、既存コードを根拠に決めて Deviations に1行残す
<!-- /scope-discipline-gap -->

<!-- scope-discipline-gap-loop -->
- 仕様（Issue・設計・直前 findings）に書かれていない判断のうち、ユーザーに見える挙動（画面の文言・表示・エラー時の挙動・並び順・権限・データの残り方・削除の可否）に関わるものは、上の「曖昧な点は解釈する」の対象外。dev-loop は途中で止まらないので、暫定案で進め、進捗ファイルの `## 要確認` に「判断内容／暫定案／根拠」を1件1行で追記する。この行は上の一文より優先する
- 要確認が1件でもあるとき、L1.5d の AskUserQuestion の本文に全件を転記し、「完了」を選ぶ前に各件がユーザーの意図に合っているかを確認する。合っていない件は「修正点を追加」で次の iteration に戻す
- ユーザーに見えない内部の判断（名前・内部の分割・既存パターンに沿った選び方）は、既存コードを根拠に決めて Deviations に1行残す
<!-- /scope-discipline-gap-loop -->
