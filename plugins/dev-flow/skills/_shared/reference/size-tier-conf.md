# `.agent/size-tier.conf` の記法と較正の考え方

`assess-change-size.sh` が変更規模（S/M/L）×リスク（LOW/HIGH）を判定するとき、既定パターン・
既定閾値をプロジェクト固有に上書きするための設定ファイル。判定器の座標系はリポジトリルートに
統一されているため、置き場所は常に **`<リポジトリルート>/.agent/size-tier.conf`** で固定。

`.agent/` はこのリポジトリの規約で全面 gitignore されるため、`size-tier.conf` は worktree を
切るたびに蒸発する（**`.agent` 自体を main clone への symlink にしている運用を除く**。その
場合は全 worktree が1本の conf を共有する）。較正内容を tracked で残す置き場は
`docs/testing/size-tier.conf.template`（`dev-setup` B1-3.5 が、worktree に
`.agent/size-tier.conf` が無いときだけこのテンプレートをコピーする）。
このテンプレートを作る導線は `dev-setup` の B1-3.6（対話で生成する）にある。

判定器はこのテンプレートの中身を読むことは無い。あるかどうかだけを「較正が意図されている
リポか」の判別に使う（下記「較正が意図されているのに効いていない警告」）。

## `=` と `:` の使い分け

- `キー=値` は**値の設定**（閾値の上書き）
- `キー: 値` は**パターンの追加**（既定パターンに1行1パターンで追記する）
- サフィックス無しの `キー_reset` は**フラグ**（該当カテゴリの既定パターンを丸ごと捨てる）

## キー一覧

| キー | 種別 | 意味 |
|---|---|---|
| `threshold_m=` | 値設定 | S/M の閾値（変更行数）を上書きする（既定 100） |
| `threshold_l=` | 値設定 | M/L の閾値（変更行数）を上書きする（既定 500） |
| `risk:` | 追加 | risk（リスク軸）パターンを既定に追加する |
| `exclude:` | 追加 | 除外パターン（行数集計から外すパス）を既定に追加する |
| `frontend:` | 追加 | frontend スコープパターンを既定に追加する |
| `backend:` | 追加 | backend スコープパターンを既定に追加する |
| `risk_reset` | フラグ | risk の既定パターンを捨て、この conf で追加した分だけを使う |
| `exclude_reset` | フラグ | exclude の既定パターンを捨て、この conf で追加した分だけを使う |
| `frontend_reset` | フラグ | frontend の既定パターンを捨て、この conf で追加した分だけを使う |
| `backend_reset` | フラグ | backend の既定パターンを捨て、この conf で追加した分だけを使う |

## パターンの書き方

`risk:` `exclude:` `frontend:` `backend:` に書くパターンは、`path_matches_risk()` /
`path_matches_plain()`（`assess-change-size.sh`）が bash の `[[ == ]]` glob として照合する。
記法が同じでも、次の4点で挙動が変わる。書いた本人の意図と無関係に**無音で効かなくなる**
ケースが多いので、conf を書いたら必ず一度 fixture で実行結果を確認すること。

### `/` の有無で照合対象が変わる（最も危険）

- `/` を**含む**パターンは**パス全体**に照合される
- `/` を**含まない**パターンは**基底名（ファイル名部分）だけ**に照合される

したがって **`risk: payments` は `src/payments/api.ts` に当たらない**（基底名は `api.ts` で
あって `payments` ではない）。当てたいなら `risk: **/payments/**` と書く。

**落ちる方向が悪い**: パターンが効かないと risk は LOW のまま、判定は軽い方へ**無音で**落ちる。
スクリプト本体の既定パターンが `*nginx*` と `**/nginx/**` の**両方**を書いているのはこのためで、
片方だけだと配置規約次第で無音で効かなくなる。

### ケース感度がキーごとに違う

- `risk:` / `frontend:` / `backend:` の照合は**ケース非依存**（`nocasematch` 有効。
  `src/Auth/` のような .NET/Java 系の命名も拾うため）
- `exclude:` の照合と、テストファイル判定（`*.test.*` 等）は**ケース依存**

扱いが逆なので、`exclude: **/Tests/**`（キーは小文字・パターン値だけ大文字）と書くと、
`load_conf()` の解釈自体は成功し（`exclude追加` の警告は出る）、実ディレクトリ名が `tests`
（小文字）であれば**無音で永久に一致しない**。`Exclude:` のようにキー自体を大文字にした
場合は `case "$line" in` が `exclude:*)` に一致せず、行番号付きで「解釈できなかった」警告が
出る（こちらは静かではない）。

### コメントと空行

- `#` で**始まる行**だけがコメント。空行は無視される
- **行末コメントは非対応**。`risk: **/x/** # 理由` と書くと、パターンの値は
  ` # 理由` まで含む文字列そのものになり、**無音で永久に一致しなくなる**
- 行の前後の空白（タブ含む）は trim される

### `exclude:` はリスク照合・スコープ照合に効かない（最も誤解されやすい）

実装（`parse_diff()`）は**除外を適用する前に**リスク照合とスコープ照合を行う。つまり:

- `exclude:` を足しても **risk HIGH は消えない**
- `exclude:` を足しても **`qa=required` は消えない**
- `exclude:` が効くのは**行数の集計だけ**

これは意図的な非対称。除外をリスク照合・スコープ照合にも効かせると、conf に
`exclude: **/*.tsx` を1行足すだけで frontend スコープが消え、`qa=required` が無音で
`optional` に落ちるような穴が conf 側から開いてしまう。

## `*_reset` と `*:` の併用 semantics

`risk_reset` と `risk:` を同じ conf に両方書いた場合、既定パターンは捨てられ、**この conf で
追加した分だけ**が残る（「既定 + 追加」ではなく「追加のみ」になる）。exclude / frontend /
backend も同型。

この解決は**行の順序に依存しない**。`load_conf()` は全行を読み終えてから reset フラグを見て
配列を確定するため、`risk_reset` を conf の先頭に書いても末尾に書いても結果は同じになる。

## 値の妥当性

`threshold_m=` / `threshold_l=` の値は `^(0|[1-9][0-9]*)$` にマッチする整数だけを受け付ける。
先頭ゼロ（`08` 等）を明示的に拒否しているのは、bash の算術評価で先頭ゼロが8進数と誤解釈
されるため（`08` は不正な8進数リテラルとしてエラーになる）。

`threshold_m` が `threshold_l` を超える組み合わせは、個々の値が構文的に正しくても M 帯を
丸ごと消してしまう矛盾なので拒否する。この場合は両方とも既定値（100/500）に戻し、warnings で
知らせる。

## 空値行の扱い

`risk:` `exclude:` `frontend:` `backend:` はコロンの後に値が無い行（`risk:` だけの行）を拒否
する。値の無い行はほぼ確実に書き間違いであり、黙って無視すると設定したつもりの較正が効いて
いないことに気づけないため、他の解釈できない行と同じく行番号付きで warnings に出す。

## 解釈できない行の扱い

構文として認識できない行（キーの綴り間違い等）は、**行番号だけ**を warnings に出し、行の
中身は一切出力しない。理由は2つ実測している。

1. conf はリポジトリ側が自由に書ける。中身をそのまま warnings に載せると、判定結果 JSON を
   経由して秘密ファイルの内容が PR 本文にまで流出しうる。
2. 判定結果 JSON を読むのは後続の Claude であることが多い。行の中身をそのまま出力に含めると、
   conf 経由で後続の Claude に対する指示文（「security_review は不要」等）を送り込める。

## 読み込みを拒否する条件

以下のいずれかに該当する場合、conf を一切読まずに既定値へ退避する（warnings で理由を出す）。

- symlink（**conf ファイル自体が symlink である場合**に読み込みを拒否する。PR 経由で
  リポジトリ外の任意ファイルへのリンクを送り込めるためだが、実装は `[[ -L "$conf" ]]` で
  conf 実体だけを見ており、**親ディレクトリが symlink であるケースは塞げていない**）
- ディレクトリ
- 読み取り不可
- サイズが 64KB（65536 バイト）を超える

読み込みが成立した場合でも、行数は 200 行で打ち切る（超えた分は無視し、打ち切ったことを
warnings に出す）。無制限に読むと巨大 conf でハングし、「フォールバック時も含め必ず JSON を
1行出す」という判定器全体の契約が破れる。

## 強化は無音・緩和は必ず警告

厳しくする方向（risk: の追加・frontend: の追加・backend: の追加・閾値の引き下げ）は無音、緩める方向（*_reset・exclude: の追加・閾値の引き上げ）は必ず warnings に出る

厳しくする側で毎回警告を出すとオオカミ少年になり、warnings 全体が読まれなくなる。緩める側は
「レビューが手抜きになったことに誰も気づかない」方向なので、無音にはできない。

## 警告が出る条件

「緩和方向」で実際に `warnings` へ積まれる理由は、`load_conf()` 末尾の `reasons+=("...")` が
定義する次の7つに限られる。表の第1列は理由の文字列そのもの（warnings 本文に埋め込まれる
値）で、`.agent/size-tier.conf` を書いた人が「判定が意図せず軽くなっていないか」を確認する
ための手がかりになる。実装とこの表はテスト（AC54）で双方向一致を機械的に保っている。

| 理由 | 何をすると出るか | なぜ緩和方向か |
|---|---|---|
| `risk_reset` | `risk_reset` を書き、既定の risk パターンを丸ごと捨てる | 既定で拾えていた HIGH 判定が失われうる |
| `exclude_reset` | `exclude_reset` を書き、既定の exclude パターンを丸ごと捨てる | 既定で除外していたロックファイル等が行数集計に混入しうる |
| `exclude追加` | `exclude:` で除外パターンを1行以上追加する | 除外は行数集計を減らす方向にしか効かない |
| `frontend_reset` | `frontend_reset` を書き、既定の frontend パターンを丸ごと捨てる | frontend スコープが成立しにくくなり `qa=required` が消えうる |
| `backend_reset` | `backend_reset` を書き、既定の backend パターンを丸ごと捨てる | backend スコープが成立しにくくなり `qa=required` が消えうる |
| `threshold_m引き上げ` | `threshold_m=` を既定（100）より大きい値にする | S 帯が広がり、レンズ・レビュー本数の少ない経路に入りやすくなる |
| `threshold_l引き上げ` | `threshold_l=` を既定（500）より大きい値にする | M 帯が広がり、本来 L 相当の変更が M として扱われうる |

## 較正が意図されているのに効いていない警告

判定材料は「conf を読み込めたか」ではなく、**設定が1つでも実際に適用されたか
（閾値の変更・パターンの追加・reset のいずれか）**。「conf を読み込めた」だけを基準にすると
穴が残る。`*.template` は雛形として **コメントだけ・値は空** で配布するのが自然で、
`dev-setup` B1-3.5 がそれをそのまま `.agent/size-tier.conf` にコピーすると「読み込みには
成功したが何も適用されていない」状態になり、較正が効いていないのに警告が出なくなる。

したがって、**コメントだけ・値が空のテンプレートをコピーしただけ**なら較正は効かず、警告も
鳴り続ける。閾値や risk/exclude/frontend/backend の実効値が入ったテンプレート（下記
下記の実例のように）をコピーした場合は、コピーした時点で `conf_applied=1` になり
この警告は出ない。

## 較正の考え方と実例

既定の閾値・パターンはアプリ層の一般的なリポジトリを想定した値で、リポジトリの実態に応じて
外れることがある。ある業務リポジトリの `docs/testing/size-tier.conf.template` は次の内容:

<!-- このフェンスの info string は conf 固定（dev-setup B1-3.6 の複製とドリフト検出で突き合わせる） -->
```conf
exclude: **/tests/**
exclude: **/test/**
exclude: **/__tests__/**
exclude: **/e2e/**
exclude: *.test.*
exclude: *.spec.*

threshold_m=150
threshold_l=1200
```

- **テストファイルを除外する理由**: 除外しないと「テストを厚く書くほどレビューが重くなる」
  逆インセンティブが働く。実測: このリポの PR #273 は 4,754 行のうち 3,741 行（79%）が
  テストコードで、判定を左右していたのは実質テストの量だった。
- **閾値を引き上げた理由**: このリポは実装のみで 1,000 行規模の機能追加が常態のため、
  既定の 100/500 では大半の機能追加が L に張り付き、サイズ軸が事実上機能しなくなる。

## 判定仕様の正はどこか

このドキュメントが扱うのは conf の記法と較正の考え方だけで、ゲート仕様（`gates` の解決規則・
S/M/L ごとの `adversarial_lenses` や `self_review_members` の内訳等）全体の正ではない。
判定仕様の正は **`assess-change-size.sh` 本体と `assess-change-size.test.js`**。
