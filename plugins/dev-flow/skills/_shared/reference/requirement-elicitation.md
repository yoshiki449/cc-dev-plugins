# 要求の深掘り手順（requirement-elicitation）

ユーザーの要求が曖昧なとき、または言われた解決策が根本の困りごとを解決しないときに、質問を繰り返して要求を確定させる手順。要求を受け取る入口（`dev-plan` A1 / `auto-spec` S1 / `dev-fix` F1）が使う。

## 境界

- **入力**: ユーザーの依頼文、それまでの回答、（あれば）Issue 本文と既存コード
- **出力**: ユーザーが復唱に合意した「確定させる項目」一式（`dev-plan` / `auto-spec` は要求カード、`dev-fix` は分類ごとの項目）
- **責務**: 要求を確定させるところまで。設計・実装方針は決めない。代替案を出すのは困りごとを解消しない解決策を指摘するときだけで、採否はユーザーが決める

## なぜ設計より前に確定させるか

- 要求の読み違いが設計レビューで見つかると、仕様設計・画面設計まで作り直しになる
- 後段の `requirement-coverage-checker` と `stop-judge` は Issue 本文を正解として達成を判定する。要求が曖昧だと、その「達成」も当てにならない
- 手段の形をした要求をそのまま仕様にすると、困りごとを解決しない機能が仕様どおりに動く。テストも QA も仕様に照らして検査するので、この欠陥は後段で検出されない

## 1. 要求カード（深掘りのゴール）

`dev-plan` と `auto-spec` は、次の5項目を埋めることを深掘りのゴールにする。`dev-fix` は自分の SKILL.md の分類表にある項目を使う。

| 項目 | 埋まったとみなす条件 |
|---|---|
| 目的 | 誰の、どの業務・操作のためかが1文で書ける |
| 現状の困りごと | 今どうなっていて何が困るかが、具体的な場面1つで書ける（「使いにくい」は不可。どの操作で何が起きるか） |
| 成功を観察する条件 | 完成後に、誰が何をすると何が見えれば成功かが書ける（観察できない「改善される」は不可） |
| スコープ外 | 今回やらないことが1件以上書ける。無い場合は「無い」とユーザーが明言している |
| 制約 | 期限・既存システム連携・データ規模・権限など、設計を縛る条件。無い場合は「無い」とユーザーが明言している |

## 2. 深掘りする条件（曖昧さの検出）

依頼文とそれまでの回答を読み、次のどれかに当たる項目を深掘りする。

- 項目が空、または「埋まったとみなす条件」を満たさない
- 程度を表す語だけで基準が無い（「速く」「見やすく」「いい感じに」「ちゃんと」）
- 対象が特定できない（「一覧」「画面」「データ」がどれを指すか2通り以上ありうる）
- 解釈が2通り以上に分かれ、どちらを取るかで実装が変わる

## 3. 解決策の妥当性チェック（本質的でない要求の検出）

依頼文が解決策（手段）の形をしている場合（「○○ボタンを足して」「○○を CSV で出して」「リトライを入れて」「このテストを skip して」）は、困りごと（`dev-fix` のバグ・テスト修復では症状と原因）を先に確かめてから、次の3問を自問する。

1. その解決策で、困りごとの場面は実際に解消するか
2. 困りごとの原因は別の場所にないか（例: 出力が欲しいのではなく、画面で絞り込めないことが原因）
3. 既存機能の使い方や小さな変更で同じ困りごとが解消しないか

どれかで「解消しない／別の案がある」となったときの扱いは次のとおり。消費側の SKILL.md はこの行を同じ文で持つ。

<!-- requirement-elicitation:alternative -->
- 解決策が困りごとを解消しないと判断したら、根拠（どの場面で何が残るか）を示して指摘し、元の案と代替案を並べて AskUserQuestion で選んでもらう
- 元の案が選ばれたら、その判断を記録してそのまま進める
- Claude が代替案で勝手に進めてはならない
<!-- /requirement-elicitation:alternative -->

## 4. 質問の出し方

- 1つの質問が持つ中身（推奨案・根拠・選択肢）は「6. 問いの書式」、どの論点をいつ聞くかは「7. 論点の仕分け」に従う
- 1往復で聞くのは最大4問（AskUserQuestion の上限）。アーキテクチャや範囲が変わる質問から先に聞く
- 自由記述で投げず、想定される答えを選択肢として並べる。質問文には前提を含め、ダイアログ単体で判断できるようにする。本文に書いた表や要約はダイアログを開いている間ユーザーから見えないので、判断に要る内容はダイアログの中に入れる
- 日付・数値など値そのものが要る質問は、具体的な値を選択肢に並べる。「該当する（詳細は『その他』で）」のような選択肢は、選ばれても値が返ってこず1往復を失う（複数選択では特に起きやすい）
- 前の回答を受けて次の質問を作る。最初に全問を決め打ちしない
- 調べれば分かること（既存コード・Issue 本文・仕様書に書いてあること）は聞かずに自分で調べる

## 5. 終了条件

消費側の SKILL.md はこの行を同じ文で持つ。

<!-- requirement-elicitation:exit -->
- 確定させる項目がすべて「埋まったとみなす条件」を満たしたら、項目を復唱してユーザーに合っているかを確認する。復唱の全文は AskUserQuestion のダイアログの中（question 文か選択肢の preview）に入れる。合意が取れたら終了し、修正が入ったら反映して再度復唱する
- 依頼文と既存の資料だけで項目が埋まるなら、質問はせず復唱1回で終える
- 3往復しても埋まらない項目は、「今ここで決める（決定内容を選択肢で提示）」か「承認済み保留（理由／いつ誰が決めるか／暫定案／影響範囲）」のどちらかで1件ずつ閉じる
- 復唱への合意が取れるまで、また未クローズの項目が残っているうちは、次の手順へ進んではならない
<!-- /requirement-elicitation:exit -->

## 6. 問いの書式（推奨案・根拠・選択肢）

問いだけを渡されると、ユーザーは白紙から判断することになる。推奨案があれば「確認」で済むが、その推奨案が調べた結果なのか推測なのかが見えないと、推測をそのまま承認してしまう。そこで、推奨案には根拠を必ず添え、根拠が無いときは推奨案を作らない。出典: [食べログ Tech Blog の記事](https://tech-blog.tabelog.com/entry/ai-requirements-definition-with-questions) の「提案・根拠・選択肢」の3点セット。

消費側の SKILL.md はこの行を同じ文で持つ。

<!-- requirement-elicitation:question-format -->
- 質問には「推奨案」「根拠」「選択肢」を付ける。推奨案は選択肢の先頭に置き、ラベルの末尾に「(Recommended)」を付ける
- 根拠は、何を読み何を実行して推奨案に至ったかを1〜2行で書く（ファイルと行、ユーザーの過去の発言の引用）。根拠が推測だけなら「推測」と明記する
- 根拠が無く推奨案を作れない質問は、推奨案を無理に作らず「推奨なし（判断材料が無い）」と明記し、判断に要る情報を選択肢の説明に書く
<!-- /requirement-elicitation:question-format -->

## 7. 論点の仕分け（工程と優先度）

論点を全部同じ重さで出すと、その場で決めなくてよい論点にもユーザーの検討時間を使わせる。一方で、仕分けを AI 任せにすると「後で決める」に流して聞かずに進む経路になる。だから優先度「高」の基準を3つに固定し、迷ったら高にし、後工程へ送る論点は必ずユーザーの承認を通す。

消費側の SKILL.md と agent はこの行を同じ文で持つ。

<!-- requirement-elicitation:triage -->
- 論点には「工程」（その論点を決めるべき工程: 要件定義／設計／実装／運用）と「優先度」（高／中／低）を付け、質問の先頭に「工程: ○○／優先度: △△」と書く。質問は、優先度が高いものから、同じ優先度なら工程が早いものから出す
- 次のどれかに当たる論点は優先度「高」にする: 回答が無いと次の工程に着手できない／後で覆ると手戻りが大きい／事業・法務・契約上、進める前の合意が必須。判定に迷ったら「高」にする。「高」から下げるときは、3つのどれにも当たらない理由を1行書く
- 優先度「高」の論点と、いま進めている工程以前の論点は、その場で決める。決めずに次の手順へ進んではならない
- 実装・運用の工程で決める論点のうち優先度が「高」でないものだけを「後工程送り」にできる。後工程送りは、承認済み保留と同じ4点（理由／いつ誰が決めるか／暫定案／影響範囲）を1件1行の表にして、まとめて1回の AskUserQuestion で承認を取る。暫定案は本文に書かない
- 後工程送りは、未解決事項を持てる文書（Issue・引継書）でだけ使う。確定時に Open Questions を0件にする文書（REQUIREMENTS.md・DESIGN.md）では使わず、工程と優先度は質問の順序づけにだけ使う
<!-- /requirement-elicitation:triage -->

## 8. 本文に書いてよいもの（根拠の3種類）

「決まっていないことを決まったように書かない」と禁止の形で書くと、何が「決まっていない」かの判定を書き手が握る。書き手が「解釈」「暫定案」「一般的にはこう」と名前を付ければ、禁止に当たらないまま本文に入る。そこで禁止をやめ、本文に書いてよいものを列挙する（列挙にないものは書けない）。

消費側の SKILL.md と agent はこの行を同じ文で持つ。

<!-- requirement-elicitation:evidence -->
- 要件・仕様・設計の本文に書いてよいのは、根拠が次の3つのどれかで、出典を示せる事項だけ。①ユーザーの発言・回答 ②読んだ・実行した結果（ファイルと行、コマンドと出力） ③ユーザーが合意した判断
- 3つのどれでもない事項は本文に書かない。書きたくなったら、それは決まっていないことなので、問いにして、答えが返るまで本文へ入れない
- 「暫定案」「想定」「仮定」「一般的にはこう」は根拠にならない。暫定案は未解決事項の暫定案欄にだけ書き、本文には書かない
- 次の手順へ進む前に、本文を『未確定／TBD／要検討／後で決める／適宜／場合による／必要に応じて／仮定／おそらく／思われる／一般的に』で検索する。未解決事項の欄の外にヒットした箇所は、根拠の3つのどれかを示せるものだけ残し、示せないものは本文から外して問いに戻す
<!-- /requirement-elicitation:evidence -->

## 9. 具体例による確認（入力 → 期待する結果）

運用で報告されたずれ方の1つが「仕様に書いてあるが、読み方が違った」だった。文章は、同じ言葉を別の意味で読んでいても、双方が合意したように見える。具体的な値を入れた例なら、同じ文章から違う結果が出たときにずれが見える。だから、文章の復唱に加えて、結果の例で確認する。

消費側の SKILL.md と agent はこの行を同じ文で持つ。

<!-- requirement-elicitation:examples -->
- 主要な業務ルール・計算・状態の変化・入力の検証ごとに、具体的な値を入れた例を「入力 → 期待する結果」で書く。種別は正常・境界・例外を1つずつ。ユーザーの言葉を言い換えず、実データに近い具体値を使う
- 例は AskUserQuestion のダイアログの中（question 文か選択肢の preview）に、番号を付けてまとめて入れ、「この結果で合っているか」を聞く。選択肢は「すべて合っている」「違う例がある」にし、「違う例がある」が選ばれたら、その例の正しい結果を、候補を選択肢に並べて続けて聞く
- ユーザーが違うと答えたら、正しい結果を本文の該当ルールに書き直し、同じ語を使う他のルールの例も出し直す
- 例を作れないルールは、曖昧な語や未定義の境界が残っているサインなので、その語を問いに戻す。例を作るために、値や結果を推測で決めてはならない
- ユーザーが「合っている」と答えた例だけを「確認済み」にする。「未確認」の例が1件でも残っているうちは、次の手順へ進んではならない。確認済みの例は、後段のテストと QA が照合する正解として本文に残す
<!-- /requirement-elicitation:examples -->

## 10. 細部の点検（実装で AI が自分で決めやすい項目）

運用で報告されたもう1つのずれ方が「仕様に書かれていない細部を、実装の段階で AI が自分で決めていた」だった。文言・失敗時の挙動・並び順のような細部は、要件を聞く段階では話題に上がりにくく、実装で初めて決める必要が出る。話題に上がるのを待たず、カテゴリを1つずつ点検して質問にする。

消費側の SKILL.md と agent はこの行を同じ文で持つ。

<!-- requirement-elicitation:detail-checklist -->
- 変更が触れる領域について、次の10カテゴリを1つずつ点検する。仕様に書かれていない項目は、既存コードやドキュメントを読んで実測できたものだけ埋め、実測できないものは問いにする（質問の書式と優先度は上の規則に従う）
- 該当しないカテゴリは「該当なし」と理由を1行書く。黙って飛ばさない
- ①表示文言: ボタン名・入力欄の名前・エラー文・確認ダイアログの文・空の状態の文
- ②失敗時の挙動: 通信失敗・入力不正・権限なし・重複・途中で中断
- ③件数と並び: 0件・1件・大量件数の見え方、並び順、既定の絞り込み、ページ分け、件数の上限
- ④入力の決まり: 必須か任意か、文字種・桁・形式、既定値、保存されるタイミング（自動保存か明示保存か）
- ⑤取り消せない操作: 削除の可否、確認の有無、取り消しの可否、論理削除か物理削除か
- ⑥権限と見える範囲: 誰が見られて、変更でき、削除できるか。他のユーザーやテナントのデータの扱い
- ⑦データの残り方: 保存するか、保持期間、履歴、既存データの移行、他の機能・外部連携との整合
- ⑧日時・数値・単位: タイムゾーン、丸め、単位・通貨、締め日や営業日の扱い
- ⑨同時操作と再実行: 二重送信、同時編集、同じ操作の再実行の結果
- ⑩通知と波及: 通知・メール・ログ、他の画面や機能への反映
<!-- /requirement-elicitation:detail-checklist -->

## 11. 操作フロー確認モック

運用で報告された3つ目のずれ方が「仕様どおりだが、画面や操作が想像と違った」だった。ASCII のワイヤーフレームは画面の配置しか示さず、操作の流れや状態の変化は見えない。動くものを触るまで気づけないので、設計レビューの前に、操作できるモックを触ってもらう。複数の方向を比べる目的の複数方向プロトタイプ（D0.5）とは別物で、仕様を1つだけ忠実に再現し、認識のずれを見つけるために使う。

消費側の SKILL.md はこの行を同じ文で持つ。

<!-- requirement-elicitation:flow-mock -->
- 画面の追加・変更（画面遷移・入力項目・状態表示のどれかが増える・変わる）を伴うときは、設計レビューの前に、主要なユーザーストーリーを最初から最後まで操作できる静的 HTML モックを1つ作り、ユーザーに操作してもらう
- モックには、正常な流れに加えて、空の状態・エラー時・件数が多い状態など、仕様に書いた状態を切り替える手段を付ける。ASCII のワイヤーフレームでは見えない状態の変化を確認するため
- モックを作るために、仕様に無い文言や挙動を仮置きしたときは、その一覧をユーザーに示して1件ずつ確認する。仮置きをそのまま残してはならない
- ユーザーが違和感を持った点は、仕様に反映して、修正後のモックでもう一度確認する。「意図と違う点は無い」とユーザーが明言するまで、設計レビューへ進まない
- 文言だけの変更など、画面遷移・入力項目・状態表示が変わらない変更は対象外にできる。対象外にするときは理由を1行書く。判断に迷ったら作る
<!-- /requirement-elicitation:flow-mock -->
