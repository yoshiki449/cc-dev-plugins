# 要求の深掘り手順（requirement-elicitation）

ユーザーの要求が曖昧なとき、または言われた解決策が根本の困りごとを解決しないときに、質問を繰り返して要求を確定させる手順。要求を受け取る入口（`dev-plan` A1 / `auto-spec` S1 / `dev-fix` F1）が使う。

## 境界

- **入力**: ユーザーの依頼文、それまでの回答、（あれば）Issue 本文と既存コード
- **出力**: ユーザーが復唱に合意した「確定させる項目」一式（`dev-plan` / `auto-spec` は要求カード、`dev-fix` は分類ごとの項目）
- **責務**: 要求を確定させるところまで。設計・実装方針は決めない。代替案を出すのは困りごとを解消しない解決策を指摘するときだけで、採否はユーザーが決める

## なぜ設計より前に確定させるか

- 要求の読み違いが設計レビューで見つかると、仕様設計・画面設計まで作り直しになる
- 後段の `requirement-coverage-checker` と `stop-judge` は Issue 本文を正解として達成を判定する。要求が曖昧だと、その「達成」も当てにならない
- 手段の形をした要求をそのまま仕様にすると、困りごとを解決しない機能が仕様どおりに動く。テストも QA も仕様に照らして検査するので、この欠陥は後段で検出されない

## 1. 要求カード（深掘りのゴール）

`dev-plan` と `auto-spec` は、次の5項目を埋めることを深掘りのゴールにする。`dev-fix` は自分の SKILL.md の分類表にある項目を使う。

| 項目 | 埋まったとみなす条件 |
|---|---|
| 目的 | 誰の、どの業務・操作のためかが1文で書ける |
| 現状の困りごと | 今どうなっていて何が困るかが、具体的な場面1つで書ける（「使いにくい」は不可。どの操作で何が起きるか） |
| 成功を観察する条件 | 完成後に、誰が何をすると何が見えれば成功かが書ける（観察できない「改善される」は不可） |
| スコープ外 | 今回やらないことが1件以上書ける。無い場合は「無い」とユーザーが明言している |
| 制約 | 期限・既存システム連携・データ規模・権限など、設計を縛る条件。無い場合は「無い」とユーザーが明言している |

## 2. 深掘りする条件（曖昧さの検出）

依頼文とそれまでの回答を読み、次のどれかに当たる項目を深掘りする。

- 項目が空、または「埋まったとみなす条件」を満たさない
- 程度を表す語だけで基準が無い（「速く」「見やすく」「いい感じに」「ちゃんと」）
- 対象が特定できない（「一覧」「画面」「データ」がどれを指すか2通り以上ありうる）
- 解釈が2通り以上に分かれ、どちらを取るかで実装が変わる

## 3. 解決策の妥当性チェック（本質的でない要求の検出）

依頼文が解決策（手段）の形をしている場合（「○○ボタンを足して」「○○を CSV で出して」「リトライを入れて」「このテストを skip して」）は、困りごと（`dev-fix` のバグ・テスト修復では症状と原因）を先に確かめてから、次の3問を自問する。

1. その解決策で、困りごとの場面は実際に解消するか
2. 困りごとの原因は別の場所にないか（例: 出力が欲しいのではなく、画面で絞り込めないことが原因）
3. 既存機能の使い方や小さな変更で同じ困りごとが解消しないか

どれかで「解消しない／別の案がある」となったときの扱いは次のとおり。消費側の SKILL.md はこの行を同じ文で持つ。

<!-- requirement-elicitation:alternative -->
- 解決策が困りごとを解消しないと判断したら、根拠（どの場面で何が残るか）を示して指摘し、元の案と代替案を並べて AskUserQuestion で選んでもらう
- 元の案が選ばれたら、その判断を記録してそのまま進める
- Claude が代替案で勝手に進めてはならない
<!-- /requirement-elicitation:alternative -->

## 4. 質問の出し方

- 1往復で聞くのは最大4問（AskUserQuestion の上限）。アーキテクチャや範囲が変わる質問から先に聞く
- 自由記述で投げず、想定される答えを選択肢として並べる。質問文には前提を含め、ダイアログ単体で判断できるようにする。本文に書いた表や要約はダイアログを開いている間ユーザーから見えないので、判断に要る内容はダイアログの中に入れる
- 日付・数値など値そのものが要る質問は、具体的な値を選択肢に並べる。「該当する（詳細は『その他』で）」のような選択肢は、選ばれても値が返ってこず1往復を失う（複数選択では特に起きやすい）
- 前の回答を受けて次の質問を作る。最初に全問を決め打ちしない
- 調べれば分かること（既存コード・Issue 本文・仕様書に書いてあること）は聞かずに自分で調べる

## 5. 終了条件

消費側の SKILL.md はこの行を同じ文で持つ。

<!-- requirement-elicitation:exit -->
- 確定させる項目がすべて「埋まったとみなす条件」を満たしたら、項目を復唱してユーザーに合っているかを確認する。復唱の全文は AskUserQuestion のダイアログの中（question 文か選択肢の preview）に入れる。合意が取れたら終了し、修正が入ったら反映して再度復唱する
- 依頼文と既存の資料だけで項目が埋まるなら、質問はせず復唱1回で終える
- 3往復しても埋まらない項目は、「今ここで決める（決定内容を選択肢で提示）」か「承認済み保留（理由／いつ誰が決めるか／暫定案／影響範囲）」のどちらかで1件ずつ閉じる
- 復唱への合意が取れるまで、また未クローズの項目が残っているうちは、次の手順へ進んではならない
<!-- /requirement-elicitation:exit -->
