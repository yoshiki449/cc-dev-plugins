# /explain-diff — 変更理解ドキュメント生成

## 位置づけ

AI がコードを書く速度が上がった結果、開発のボトルネックは「コードを書くこと」から「人間がコードを理解すること」に移った。このスキルは、コード変更をただ要約するのではなく、**読者が創造的プロセスに参加し続けられるだけの理解**を作ることを目的とする。

- 出典: Geoffrey Litt「Understanding is the new bottleneck」（2026-07-02）と同氏の explain-diff プロンプト
- クイズは「AI のループを人間の理解速度に合わせる速度レギュレーター」として機能する（Andy Matuschak の理解度確認の発想）
- dev-flow では auto-build / auto-feedback の完走後（Finalize）、dev-verify D6.5（全 Phase 完了時）、dev-qa Q5.5 から自動生成される（ship 前の人間レビューに間に合わせる配置）。dev-ship E2.5 は生成済み HTML の再利用が基本（無ければ生成）。手動ではいつでも `/explain-diff` で起動できる

## 引数

```
/explain-diff [対象]
```

対象の解釈（上から順に判定）:

| 指定 | 例 | diff の取り方 |
|---|---|---|
| 省略 | `/explain-diff` | `git diff origin/main..HEAD`（現在のブランチ全体） |
| コミット範囲 | `/explain-diff 4479b93..HEAD` | `git diff <範囲>` |
| PR 番号 | `/explain-diff #42` | `gh pr diff 42`＋`gh pr view 42` で本文・Issue も読む |
| ブランチ名 | `/explain-diff feature/foo` | `git diff origin/main..feature/foo` |

差分が空のときは「説明対象の変更がない」と報告して終了する（空の説明を生成しない）。

## 手順

### X1. 対象 diff の確定

上の表に従って diff を取得する。あわせて `git log --oneline` で対象範囲のコミットメッセージ、関連する Issue / PR 本文があればそれも読む（変更の「意図」の一次情報になる）。

### X2. 周辺コードの探索 ⚠ 省略禁止

diff だけを読んで書き始めてはならない。**変更されたファイルの周辺コードを広く探索**し、既存システムがどう動いているかを先に把握する:

1. 変更された各ファイルの変更前の姿（該当関数・モジュール全体）を Read する
2. 変更箇所を呼び出している側・呼び出されている側を Grep で辿る
3. プロジェクトの README / 設計ドキュメント（DESIGN.md / REQUIREMENTS.md / .agent/ 配下）があれば読む

背景セクションの質はこの探索量で決まる。

### X3. 説明 HTML の生成

以下の4セクション構成で、**単一の自己完結型 HTML**（CSS / JavaScript 内包、外部リソース参照なし）を生成する。

#### 1. 背景（Background）

変更に関連する既存システムを説明する。読者の前提知識は不明なので2段構えにする:

- **深い背景**: 初心者向けに、関連するシステム全体の仕組みから説明する。冒頭に「すでに詳しい方はこの節を読み飛ばして構いません」の注記を付ける
- **直接の背景**: この変更に直結する狭い範囲の背景。変更前のコードがどう動いていたか

#### 2. 直感（Intuition）

変更の核となる考え方を説明する。**全詳細ではなく本質**に絞る:

- トイデータを使った具体例で説明する（「ユーザー A が X をすると…」）
- 図・ダイアグラムを多用する
- 「なぜこの方法なのか」「他の素朴な方法だと何が困るのか」に触れる

#### 3. コード解説（Code）

変更の高レベルウォークスルー。ファイル順ではなく、**理解しやすい論理的な順序**でグルーピングして説明する（例: データモデル → コアロジック → UI → テスト）。各グループで代表的なコード片を `<pre>` で引用する。全行を貼らない。

#### 4. 理解度クイズ（Quiz）

中難度の選択式問題を **5問** 作る:

- 変更の本質を理解していないと答えられない難度。ただし引っ掛け問題は禁止
- 目的は採点ではなく「読者が本当に理解できたかのセルフチェック」
- 各問4択程度。**選択肢をクリックすると即座に正誤が表示され、なぜ正しい/間違いかの解説が出る** インタラクティブ形式（JavaScript で実装）
- 最後に「5問中◯問正解」の集計表示があるとよい

### X4. フォーマット規約 ⚠ 必須

- **1ページ縦長構成＋冒頭に目次**（アンカーリンク）。タブでの切り替え構成は禁止
- スマホでも読める簡易レスポンシブ（`max-width` と `viewport` メタタグ程度でよい）
- **日本語**で書く。明晰で流れの良い文章（です・ます調）。セクション間の遷移を滑らかにし、箇条書きの羅列で済ませない
- **図は ASCII アート禁止**。簡易 HTML（div + flexbox / grid + 枠線）で描く。図のファミリーを少数（2種類程度）決めて使い回すと読者が図の読み方を学習できる:
  - 簡易 UI モック（UI 変更の説明用）
  - コンポーネント間のデータフロー図（**必ず実例データを載せる**）
- **コードブロックは `<pre>` タグ必須**。カスタム div を使う場合は CSS に `white-space: pre` または `pre-wrap` を必ず付ける（無いとブラウザが改行を潰して1行になる）。**保存前に HTML 内の全コードブロックを走査して、この CSS が付いているか検査すること**
- 重要概念・定義・エッジケースは**コールアウトボックス**（色付き囲み）で強調する

### X5. 保存と提示

1. 保存先は**対象リポジトリの `.agent/explanations/`**（ドキュメント保管規約。`.agent/` は gitignore 対象なのでバージョン管理を汚さない）。`mkdir -p <repo>/.agent/explanations` してから保存する
   - git リポジトリ外で実行された場合のみ `~/.claude/explanations/` にフォールバック
2. ファイル名は **`YYYY-MM-DD-<slug>.html`**（今日の日付プレフィックス。時系列ソートのため必須。slug は変更内容を表す英小文字ケバブケース）
   - 例: `<repo>/.agent/explanations/2026-07-07-add-auth-middleware.html`
3. **実行マニフェスト**（dev-hub の実行履歴ビュー用）に記録する（リポ内保存時のみ）:
   ```bash
   node skills/_shared/scripts/hub-run-add.mjs --repo <repoルート> \
     --run issue-<Issue番号>（Issueなしなら <YYYYMMDD-HHMM>-<slug>） \
     --label "<変更内容の短い説明>" --flow explain-diff \
     .agent/explanations/YYYY-MM-DD-<slug>.html
   ```
4. 生成後、ユーザーに以下を提示する:
   - ファイルの絶対パス
   - `wslview <パス>`（WSL）または `xdg-open <パス>` でブラウザで開けること。ユーザーが望めば実行する
   - 4セクションの1行ずつの見出しサマリ（HTML を開かなくても何が書いてあるか分かる程度）

## 禁止事項

- diff だけ読んで周辺コード探索なしに書き始める（X2 省略禁止）
- 外部 CDN・外部画像への参照を含む HTML を生成する（自己完結が壊れる）
- クイズを飾りにする（クリックしても反応しない静的リスト、答えが本文の丸写しで考えなくても解ける問題）
- `.agent/explanations/` 以外のリポジトリ内の場所（docs/ やルート直下等の tracked な場所）に HTML を保存する（バージョン管理を汚す）
- シークレット（トークン・パスワード等）が diff に含まれる場合、それを HTML に転記する
