# /auto-spec - 要件定義フェーズ（人間タッチポイント1）

## 概要

autopilot ハーネスの **3つの人間タッチポイントのうちの最初の1つ**。要件をユーザーから引き出して REQUIREMENTS.md ドラフトを生成し、人間レビューで Open Questions を解消して確定する。

このスキルは **Workflow ツールを起動しない**（軽量・メインセッション完結）。

## 入力

- ユーザーから自然言語で受け取る機能要件・背景・目的
- 既存リポジトリがあればその構造

## 手順

> **フェーズ開始時の共通前処理**: `mkdir -p .agent && git branch --show-current > .agent/.dev-flow-active` を実行してフェーズマーカーを書き込む（suggest-dev-phase hook のフェーズ想起案内を沈黙させる。`/dev-ship` E7 が掃除する）

### S0. プロジェクト判定

1. `git status` でリポジトリ状態を確認
2. `git ls-files | head -50` で既存構造を把握（新規プロジェクトなら空）
3. 既存 `REQUIREMENTS.md` がないか確認。あれば「更新するか／新規セクションを足すか」を AskUserQuestion で確認

### S1. ヒアリング

要求は [要求の深掘り手順](../_shared/reference/requirement-elicitation.md) に従って深掘りする。後段の AI 自律ループは REQUIREMENTS.md を前提に走るので、ここで要求を確定させないと誤った前提のまま最後まで走る。

**質問順の原則**: 回答次第でアーキテクチャや技術選定が変わる質問（データ規模・同時利用者数・認証方式・既存システム連携・リアルタイム性の要否など）を優先して**先に**聞く。文言や画面の細部はその後で良い。

1. **要求カード**を埋める: 目的／現状の困りごと／成功を観察する条件／スコープ外／制約。項目が空・程度を表す語だけ・対象が2通り以上に読める・解釈で実装が変わる、のどれかに当たる項目は質問で掘り下げる
2. **解決策の妥当性チェック**: 依頼が「○○を足して」のような手段の形なら、困りごとを先に聞き、その手段で困りごとが解消するかを確かめる
   <!-- requirement-elicitation:alternative -->
   - 解決策が困りごとを解消しないと判断したら、根拠（どの場面で何が残るか）を示して指摘し、元の案と代替案を並べて AskUserQuestion で選んでもらう
   - 元の案が選ばれたら、その判断を記録してそのまま進める
   - Claude が代替案で勝手に進めてはならない
   <!-- /requirement-elicitation:alternative -->
3. 要求カードに加えて、以下を AskUserQuestion で確認する（既にユーザーが入力済みなら省略可）:
   - **対象ユーザー**: 誰が使うか
   - **主要なユーザーストーリー**: 「Aの立場でBをしたい、なぜならC」を最低1〜3個
   - **非機能要件**: 性能・対応ブラウザ・アクセシビリティ・国際化など気にすることがあれば
   - **ドメイン・コードベースへの習熟度**: このドメイン・コードベースへのユーザーの習熟度（初見／触ったことがある／熟知）。1往復目の質問に含める。REQUIREMENTS.md のメタ情報に記録し、後段の説明粒度・確認頻度の調整に使う
4. 終了条件:
   <!-- requirement-elicitation:exit -->
   - 確定させる項目がすべて「埋まったとみなす条件」を満たしたら、項目を復唱してユーザーに合っているかを確認する。復唱の全文は AskUserQuestion のダイアログの中（question 文か選択肢の preview）に入れる。合意が取れたら終了し、修正が入ったら反映して再度復唱する
   - 依頼文と既存の資料だけで項目が埋まるなら、質問はせず復唱1回で終える
   - 3往復しても埋まらない項目は、「今ここで決める（決定内容を選択肢で提示）」か「承認済み保留（理由／いつ誰が決めるか／暫定案／影響範囲）」のどちらかで1件ずつ閉じる
   - 復唱への合意が取れるまで、また未クローズの項目が残っているうちは、次の手順へ進んではならない
   <!-- /requirement-elicitation:exit -->

### S2. spec-writer の起動

`dev-flow:spec-writer` エージェントを起動し、以下を渡す:
- ヒアリング結果（S1 で合意した要求カード5項目を含む。スコープ外は REQUIREMENTS.md のスコープアウトに、成功を観察する条件は機能要件の検証条件に反映させる）
- 既存リポジトリ構造
- 出力先パス: `docs/REQUIREMENTS.md`（ドキュメント保管規約。ルート直下には置かない）

spec-writer は Open Questions に最低1件は何かを残す。完璧と思ってもそうする（検証粒度・前提・対象ブラウザ等を確認）。

### S3. 人間レビュー（TP1）

1. 生成された `REQUIREMENTS.md` の内容をユーザーに提示
2. **Open Questions セクションがある場合**: AskUserQuestion で1問ずつ回答を求める
3. 回答を `REQUIREMENTS.md` に反映（Open Questions セクションは消し、本文に統合）
4. ユーザーから「他にも修正したい箇所がある」と言われたら、自然言語で受けて反映

### S4. 確定

1. ユーザーに最終確認: 「この内容で確定し、次の設計フェーズ（/auto-design）に進めますか？」
2. 確定後、`docs/REQUIREMENTS.md` を Git に追加してコミット: `docs: 要件定義書を確定`
3. 次のアクション提示: 「/clear して `/auto-design` に進めますか？」

## 出力

- `docs/REQUIREMENTS.md`（確定版・Open Questions セクションなし）
- コミット 1 つ

## 確定の判断基準

- ユーザーストーリーの「検証」欄が**観察可能**な記述になっていること
- スコープアウトが明示されていること
- 非機能要件のうち重要なもの（性能・対応ブラウザ・a11y）が判断されていること
- Open Questions が0件

これらを満たさない状態で確定してはならない（後段の AI 自律ループが誤った前提で走る）。

## Workflow ツールについて

このスキルは Workflow ツールを起動しない。**自律完走を必要としない人間タッチポイントのため**。

## Stop（このスキルが超えてはいけない境界）

Loop Engineering の Stop 原則を、ループしないこのスキルにも適用する:

- **Never auto-approve**: `REQUIREMENTS.md` 生成後、人間レビュー（TP1）を必ず経由する。スキル自身が「確定」状態にしない
- **Never invoke /auto-design without TP1 sign-off**: 人間が REQUIREMENTS.md を承認するまで次フェーズへ進めない
- **Anything uncertain → 質問**: 要件が曖昧な箇所は AskUserQuestion で確認し、推測で書き残さない

## 次フェーズ

- 確定後 → `/auto-design`（人間タッチポイント2）
