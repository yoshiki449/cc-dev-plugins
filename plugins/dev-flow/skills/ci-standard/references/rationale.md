# ci-standard の根拠

## 発端の実測

ある PoC リポジトリ（private）で、AI エージェントの利用により PR・commit・push が増え、GitHub Actions の利用量が増えた。全 48 run の履歴と、代表 2 run の job 詳細から次を確認した（2026-09 時点）。

| 項目 | 実測 |
|---|---|
| 月間の Actions Linux 利用量 | 472 分（総額 $2.83、無料枠を引いた請求額 $0.73） |
| 成功した run 1 回あたり | 約 13.5 job 分（job ごとに分単位で切り上げた推定） |
| E2E（2 ブラウザ）の占める割合 | 約 7〜8 分で、1 run の約 55% |
| docs だけの変更で走った run | 48 run 中 5 run（README のみ） |
| main への push の run | 48 run 中 16 run。PR とほぼ同一内容 |
| キャンセルされた run | 0 件（同一ブランチの連続 run は前の run が終わってから始まっていた） |
| Actions storage | 9.99 GB-hr で 0.01 ドル未満（見直しの効果が無い） |

## 標準にした変更と見込み

- PR・push の run: 約 13.5 job 分 → 約 6 分（E2E を外し、lint / unit のみ）。実機で約 6 分を確認した。
- 週次の E2E run: 約 14 job 分 + 通知 1 分。
- 月間: 同じ run 数なら約 472 分 → 約 270 分（約 4 割減。推定）。
- docs だけの変更: 0 分。

## トレードオフ

- **E2E の不具合検知が最大 1 週間遅れる。** 過去に、PR では通ったがマージ後の E2E で失敗して追従修正した事例があった。UI・認証・DB スキーマを変える PR は、マージ前に手動実行（`workflow_dispatch`）で E2E を実行する運用で補う。
- **本番影響が大きいリポジトリは例外にする。** 遅延の許容度は、デプロイの自動化・公開範囲・扱うデータで決まるため。

## 踏んだ落とし穴（実測）

1. **`curl` は `--fail-with-body` が無いと、HTTP 403 でも終了コードが 0 になる。** Webhook の token を誤っても run が成功扱いになり、通知失敗に気づけない。最初のテストは HTTP 500 しか見ておらず、このフラグの除去を検知できなかった（500 は `--retry-all-errors` の副作用で非ゼロになる）。403 のテストを足して検知できるようにした。
2. **通知 job に `always()` が無いと、E2E が失敗したときや、前段の失敗で E2E が skipped になったときに通知 job も skipped になる。** 失敗を通知できなくなる。
3. **`concurrency` の group が ref 単位のまま `cancel-in-progress: true` だと、連続マージで先の main の検証が消える。** PR 番号（PR 以外は commit の SHA）で分け、キャンセルは PR のみにする。
4. **skipped になった matrix job の表示名は `E2E (${{ matrix.browser }})` のまま展開されない。** その名前を required check にできない。
5. **`paths-ignore` と required status checks の組み合わせ。** 起動しなかった check は pending のままになり、マージできない。
6. **`schedule` はデフォルトブランチの workflow だけが対象。** マージ前には実機で確認できない。初回は `workflow_dispatch` で確認する。
7. **Webhook URL は `key` と `token` を含む。** コードに書かず Secret から読む。ブランチ名などの値は `env` 経由で渡し、`run:` に式（`${{ }}`）を直接埋め込まない（スクリプトインジェクション）。
8. **YAML 1.1 の解析では `on` が真偽値 `True` のキーになる。** PyYAML で workflow を読むときは `wf["on"]` と `wf[True]` の両方を見る。

## 通知先の考え方

| 案 | 長所 | 短所 |
|---|---|---|
| 全リポジトリを 1 スペースに集約（推奨） | 設定が 1 回。失敗が 1 か所に並ぶ。週次なので件数は「リポジトリ数 / 週」 | スペースの閲覧者に全リポジトリの結果が見える。Webhook を再発行すると全リポジトリの Secret を更新する |
| プロジェクトごとにスペースを分ける | 通知が関係者だけに届く。Webhook の影響範囲が限られる | スペースの作成と Secret の登録が、リポジトリごとに増える |

Google Chat の Webhook はそのスペースへの投稿だけができる。通知本文にリポジトリ名を入れるので、集約しても区別できる。閲覧者を分けたい案件だけ、Secret の値を別スペースの Webhook にする（コードの変更は不要）。

## 検証の位置づけ

- 判定（`validate_ci.py`）は、各リポジトリの CI に組み込まず、`/dev-setup` の B5.6（開発に着手したとき）に実行する。リポジトリごとに適用を判断する運用のため、CI 内で強制すると、例外にしたリポジトリや未適用のリポジトリで常に失敗する。
- 標準を変えたときの回帰は、このスキルのテスト（`ci-standard.test.mjs`）が検知する。標準から外した設定を 25 通り作り、該当ルールが不適合を出すことと、通知スクリプトが実際の HTTP 送信で正しく動くことを確かめる。
