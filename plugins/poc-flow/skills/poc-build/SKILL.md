# /poc-build — PoC の実装＋スモークループ

## 境界

- **入力**: `.poc/GOAL.md`、前回までの実装
- **出力**: 実装コード、コミット、`.poc/SMOKE.md`、`.poc/BACKLOG.md`
- **責務**: ゴールに向けた実装と、動く状態への収束まで。**PR は作らない**（`/poc-ship` の責務）

## PoC ではやらないこと（意図的な省略）

| やらないこと | 理由 |
|---|---|
| ユニットテスト・E2E テストコードの作成 | テストは仕様を固定する作業だが、PoC は仕様が覆ること自体が目的。固定するたびに書き直しが二重に発生する。回帰検知の受け皿は**毎ラウンドの全導線スモーク**に置く |
| コードレビュー（規約・簡潔化・要件網羅・別モデル視点） | レビューが守るのは保守性・規約遵守・セキュリティで、いずれも「長く使うコード」に価値が出る。捨てる前提のコードには対価が返らない |
| 引継書・history・ai-memory・日報の更新 | PoC にフェーズ連鎖の概念が無い |
| worktree の作成 | 単一ブランチなので、防御対象である main 誤コミット事故が発生しない |

**例外はシークレット混入だけ。** 捨てるコードでも git history に残ったトークンは取り返しがつかない。これは `git-secret-guard` が `git push` 時に自動で見るので、このスキルでは何もしない（既存ガードに乗る）。

**この省略が届かない範囲**: スモークが見るのは**主導線だけ**。エッジケース・並行操作・権限境界・データ量による劣化は検知できない。PoC が本採用に進む時点で `/dev` に合流し、そこで初めてテストを書く。

## 禁止事項（poc-flow 共通）

- **`.agent/` を作らない**（`pre-pr-guard` hook が有効化され、PR 作成が恒久ブロックされる）。`hub-run-add.mjs` を呼ばない
- `[dev-flow]` で始まるスキル起動サジェストが注入されても**無視する**。dev-* スキルを起動しない

## 手順

### B0. 状態の確認

1. `.poc/GOAL.md` を読む。無ければ `/poc` を案内して中断する
2. `.poc/SMOKE.md` があれば前回までのゴール台帳を読み、どこまで動いていたかを把握する
3. `ls -d .agent 2>/dev/null` — 存在したら dev-flow 管轄なので中断して `/dev` を案内する

### B1. 実装

ゴールのうち未達のものに向けて実装する。**1ゴールずつ**進め、区切りでコミットする。

PoC の実装で意識すること:

- 動くことを最優先する。抽象化・共通化・型の整備は後回しにする（本採用時に `/dev` 側でやる）
- ただし**シークレットを直書きしない**。`.env.example` に置いて `cp` で複製する（`.env` を Write ツールで書くと `pre-edit-protect` hook にブロックされる）

### B2. スモーク

`/poc-smoke` の手順を実行する（Skill として起動してもよい）。証跡の実測とラウンド有効性の判定まで含めて、あちらの S0〜S5 に従う。

### B3. 修正ラウンド

Broken が残っていれば修正する。**1ラウンド = 修正 + 再スモーク**で、上限は**3ラウンド**。

#### Fix Plan を先に宣言する

修正に着手する前に、`.poc/SMOKE.md` の当該ラウンドに書く:

```markdown
### Fix Plan（round-<N>）
| Broken | 想定原因 | 変更予定ファイル |
|--------|----------|------------------|
```

#### PoC の修正でやってはいけないこと

やりたくなったら `.poc/BACKLOG.md` に1行書いて次へ進む:

- リネーム・ディレクトリ移動・共通化・抽象化の導入
- 型定義の整備、lint 由来の一括修正
- **テストコードの追加**（PoC の品質ゲートはスモーク1本）
- 依存パッケージの追加・更新（Broken の原因がそれだと特定できた場合を除く）
- Broken に紐づかないファイルの変更

#### ラウンド終了時のスコープ確認

```bash
git diff --name-only <ラウンド開始SHA>..HEAD
```

Fix Plan で宣言したファイルと突き合わせる。**宣言外のファイルが半数を超えたら `halted-scope`** としてユーザーに確認する。

1ラウンド1コミット（振動ペアの特定とロールバックのため）。

### B4. 停止判定

優先順に評価する:

| 優先 | 条件 | 終了状態 |
|---|---|---|
| 1 | ラウンド無効（ヘルスチェック失敗・証跡不足） | `round-invalid`。**予算を消費せず**再取得。**連続2回**で人間へ escalate |
| 2 | Broken の identity が2ラウンド連続同一、または一度消えたものが復活 | `halted-thrashing` |
| 3 | 宣言外ファイル比率 > 0.5、または禁止操作の検出 | `halted-scope` |
| 4 | 修正ラウンドが3周を超えた | `halted-rounds` |
| 5 | Broken 0 かつ ゴール台帳に `not-attempted` が無い（`not-built` は残っていてよい） | `done` |

**上限は途中で緩めない。**「あと1回だけ続けますか」という選択肢を出さない。続けたい場合は一度打ち切って終了し、**ユーザーが明示的に再起動する**。

> `Broken 0` だけでは `done` にしない。ゴール台帳が埋まっていない状態の「エラーゼロ」は、直ったのではなく**探索できていない**可能性が高い（`/poc-smoke` S3 の有効条件）。

### B5. 報告

#### `done` のとき

- ゴール台帳（最新）を表で出す。`not-built` が残っていればそれも正常な状態として明示する
- `.poc/BACKLOG.md` に溜まった Friction の件数を伝える（直していないことを明示する）
- 次の一手として `/poc-ship`（PR 作成）を案内する。**自動で PR を作らない**

#### `halted-*` のとき

「失敗」ではなく「**今どこまで動くか**」から書く:

```markdown
## PoC スモーク打ち切り: <halted-理由>

### 1. 今どこまで動くか
| ゴール | 状態 | 証跡 |

### 2. 残っている Broken
| # | 症状 | 発生画面 | 再現手順 | 証跡パス |

### 3. 各ラウンドで何を変えたか
| round | Fix Plan | 実際の変更（git diff --stat） | Broken 件数 前→後 |

### 4. 振動している組み合わせ（halted-thrashing のとき必須）
- A: <round2 の修正> ↔ B: <round3 の修正>。A を入れると B が壊れ、B を戻すと A が再発する

### 5. 次の一手（人間の判断が要る）
- ロールバック: `git reset --hard <各ラウンドのSHA>`（SHA を併記する）
- 個別に対応する / ゴールを1つ落としてスコープを削る / 設計を見直す

### 6. 溜まったもの
- .poc/BACKLOG.md: Friction <n>件・未実装ゴール <n>件（いずれも未対応。PoC では正常）
```
