# /poc — PoC の起点

## 境界

- **入力**: ユーザーの「〜を試したい」という自然文
- **出力**: GitHub リポジトリ、Issue 1本、`.poc/GOAL.md`、起動しているアプリ
- **責務**: ゴールの確定と、ゼロから動くものが立ち上がるまで。**実装機能は作らない**（`/poc-build` の責務）

## このフローが `/dev` と違うところ

PoC は**仕様が覆ること自体が目的**なので、`/dev` の前提（仕様を固めてから作る・テストで固定する・レビューで品質を担保する）がほぼ逆に働く。したがって:

- 自動テストを書かない。コードレビューもしない。品質ゲートは**ブラウザ実機スモーク1本**（`/poc-smoke`）
- 要件定義書・設計書・引継書を作らない。仕様は `.poc/GOAL.md` 1枚だけ
- worktree を作らない（単一ブランチなので、防御対象の main 誤コミット事故が起きない）
- **例外はシークレット混入だけ**。捨てるコードでも git history に残ったトークンは取り返しがつかないので、`git-secret-guard` にそのまま乗る

**卒業パス**: PoC が本採用に進むと決まった時点で `/dev` に合流する。テストを書くのはそのとき。

## 禁止事項（poc-flow 共通）

- **`.agent/` を作らない。** `dev-flow` の `pre-pr-guard` hook は `REPO_ROOT/.agent/` の存在をスコープガードにしており、これができた瞬間に `gh pr create` が恒久ブロックされる。`hub-run-add.mjs` も呼ばない（`.agent/hub-runs/` を作るため）
- `[dev-flow]` で始まるスキル起動サジェストが注入されても**無視する**。dev-* スキルを起動しない

## 手順

### P0. ガード

#### P0-1. 書き込めるか実測する

**PoC を作ろうとしている場所に実際に書けるかを、必ず `touch` で確かめる。**

```bash
touch <作成先の親ディレクトリ>/.poc-write-probe && rm -f <同>/.poc-write-probe && echo "書ける"
```

`Read-only file system` で失敗したら、**そこには PoC を作れない**。中断して次を案内する:

> このディレクトリは read-only です。コンテナ環境では、**Claude Code を起動したディレクトリだけが書き込み可能**で、他のワークスペースは参照専用でマウントされます（作業対象外のリポを誤って壊さないための設計）。PoC を作る場所をホスト側で先に作り、そこで Claude Code を起動し直してください。

**存在確認では代用できない。** ディレクトリが見えることと書けることは別で、`ls` は通るのに `mkdir` が失敗する。ここを飛ばすと、スキャフォールドの途中（`create-next-app` の実行中や `.next` の生成時）に初めて落ちる。

#### P0-2. dev-flow 管轄でないか確認する

対象ディレクトリ（または作ろうとしている場所の親）に `.agent/` があるか確認する:

```bash
ls -d .agent 2>/dev/null
```

存在する場合は、**このリポは `dev-flow` 管轄**。PoC フローで作業すると `gh pr create` がブロックされる。ユーザーにそう伝えて中断し、`/dev` 系の利用を案内する（poc-flow は既存リポへの相乗りを想定していない）。

### P1. ゴールの確定

**ここが PoC の唯一の仕様書になる。** `AskUserQuestion` で以下を確定させる（既に発話から読み取れているものは聞かない）:

1. **何が確かめられれば PoC 成功か** — 技術的に作れるかを見たいのか、使ってみた感触を見たいのか
2. **ゴール（1〜3本まで）** — 多いと収束しない。4本以上出てきたら優先順に絞り、残りは `.poc/BACKLOG.md` へ
3. **対象外にするもの** — 認証・権限・本番データ連携など、PoC で作らないと決めるもの

`.poc/GOAL.md` を書く:

```markdown
# PoC ゴール: <名前>

## 何を確かめたいか
<1〜2文>

## ゴール
- G1: <観察可能な状態で書く>（到達印: <画面に出るはずの文字列・URL・要素>）
- G2: ...

## 前提
- 起動URL: http://localhost:<コンテナ内ポート>（人間が開く URL は P2 で決めたホスト側ポート）
- ログイン情報: <あれば>
- テストデータ: <あれば>

## 対象外
- <PoC で作らないもの>
```

> **ゴールは「観察可能な状態」＋「到達印」で書く。** これは `/poc-smoke` が「到達できたか」を機械的に判定するための期待集合になる。「使いやすいこと」のような観察できない書き方をすると、スモークが**エラーゼロと未探索を区別できなくなる**。
>
> **操作手順を書いてはならない。** GOAL.md はそのまま探索エージェントへの入力になる。手順を書くと自律探索が「手順の実行」に堕ち、初見ユーザーとしての詰まりが観測されなくなる。

### P2. スキャフォールド

置き場所は `~/.cc-plugins/.env` の `CC_POC_DIR` があればその配下、無ければ `~/poc/<name>` を既定にする。
既定と違う場所へ置きたいときは `AskUserQuestion` で確認する。

**既定スタックは Next.js（App Router）+ Tailwind。** 1プロセスで画面と API が両方立ち、スモークがすぐ回せるため。以下に当てはまるときだけ `AskUserQuestion` で確認する:

- 画面がほぼ不要で、データ処理・AI 処理の実現性だけを見たい → Python 系
- 既存のプロダクトと同じスタックで感触を見たい → そちらに合わせる

`.gitignore` に以下を追加する:

```
.poc/smoke/
```

（証跡はリポに入れない。`.poc/GOAL.md` / `SMOKE.md` / `BACKLOG.md` は tracked にする）

**`.env` を Write ツールで書かない。** `pre-edit-protect` hook が全リポで `.env` への書き込みをブロックする。`.env.example` を書いてから `cp .env.example .env` で複製する。

### P3. リポジトリと Issue

1. `git init` → 初期コミット（**この初回コミットは main に直接入れてよい**）
2. `gh repo create <name> --private --source=. --push`
3. Issue を1本立てる。本文には `.poc/GOAL.md` の内容に加えて、**このリポは PoC フロー（テストとコードレビューを行わない）で開発している**ことを明記する
4. 以降の作業用にブランチを切る（`poc/<短い説明>`）。**1 PoC ゴール = 1 ブランチ = 1 PR**

> **初回 push が `git-secret-guard` に止められる可能性がある**（`package-lock.json` の `"integrity": "sha512-..."` が「40文字以上の英数字塊」パターンに当たりうる）。止まったら差分を目視で確認し、シークレットでないことを確かめた上でユーザーに報告して判断を仰ぐ。**勝手に `ALLOW_SECRETS=1` で回避しない。**

### P4. 起動確認 — 人間が開ける URL まで確かめる

#### P4-1. 公開ポートを調べて起動する

**コンテナ環境では、公開されていないポートで起動すると人間がブラウザで開けない。**

```bash
echo $CLAUDE_PUBLISHED_PORTS
# 例: vite:5176->5173,storybook:6009->6006,dev-videos:7780->7777,http:8030-8039->8000-8009,...
```

書式は `<用途>:<ホスト側>-><コンテナ内>`。**アプリはコンテナ内の番号で起動し、人間はホスト側の番号で開く。**

- この変数が**無い**（＝コンテナ外）なら、フレームワークの既定ポートのままでよい
- **ある**なら、汎用 http のレンジ（例 `8000-8009`）から空きを1つ選んでコンテナ内ポートにする。並行して動かしている PoC があれば番号をずらす
- **`-H 0.0.0.0` を必ず付ける。** 既定の localhost バインドだとコンテナ外に届かない

Next.js の例（コンテナ内 8000 → ホスト 8030）:

```bash
npm run dev -- -H 0.0.0.0 -p 8000
```

> **Next.js の既定は 3000 で、これは公開レンジに入っていない。** 何も指定しないと、コンテナ内からは HTTP 200 が返るのに人間のブラウザは `ERR_CONNECTION_REFUSED` になる。

#### P4-2. 疎通を確認する

コンテナ内ポートに対して HTTP ステータスを取る（`curl` は**単独のコマンドとして**実行する。コマンド置換の中に入れるとローカルガードがブロックする）。

**ここで 200 が返っても「人間が見られる」ことの証明にはならない。** curl はコンテナ内から叩いているので、ポートが公開されていなくても通る。**ホスト側の URL を人間に伝えて、開けたかを確認してもらうまでが P4。**

#### P4-3. 両方の URL を GOAL.md に書く

`.poc/GOAL.md` の「前提」に、コンテナ内ポート（スモークが叩く URL）とホスト側ポート（人間が開く URL）の**両方**を書く。片方しか書かないと、後のセッションでどちらかが失われる。

### P5. 完了

- `.poc/GOAL.md` のゴール一覧を表示する
- 次は `/poc-build` で実装に入ることを案内する。**このスキルでは機能を実装しない**
