# poc-flow

PoC（試作・実現性検証）専用の軽量開発フロー。**品質ゲートを「ブラウザ実機スモーク」1本に集約**し、自動テストとコードレビューを行わない。

## なぜ dev-flow と別にするのか

`dev-flow` は「長く保守するコードを、非エンジニアのレビューにも耐える形で本番に出す」ための一式で、最短経路でも約40ステップ（初回は約53）ある。その重さの主因は worktree 規約・サイズ判定に連動しない security 系・規模に連動しない ship の記録ステップで、いずれも**PoC には防御対象が存在しない**。

一方で PoC を「無検査で作る」と、人間がブラウザを触った瞬間にエラーを踏み、その報告作業が発生する。`poc-flow` はここだけを機械化する。

## 設計の核: 探索を subagent に分ける

メインセッションは実装を知っているので**初見ユーザーとして探索できない**。「このボタンは押せば動くはず」と知った状態でクリックすると、ラベルが分かりにくい・遷移先が想像できないといった詰まりを踏まずに通過してしまう。

- **探索** = `poc-flow:poc-smoke-explorer`（ゴールだけ渡す。操作手順・実装状態・前回の指摘は渡さない）
- **評価と修正** = メインセッション（証跡を実測で読んで判定 → そのまま直す）

評価用エージェントは増やさない。`dev-flow` が `loop-supervisor` / `stop-judge`（別モデル）で判定していることは、**期待集合（GOAL.md のゴール）を先に固定する**ことで機械的チェックに落としている。

## スキル

| スキル | 入力 | 出力 | 責務 |
|---|---|---|---|
| `/poc` | 「〜を試したい」という自然文 | GitHub リポ・Issue・`.poc/GOAL.md`・起動中のアプリ | ゴールの確定と、ゼロから動くものが立ち上がるまで。実装機能は作らない |
| `/poc-build` | `.poc/GOAL.md`、前回までの実装 | 実装コード・コミット・`.poc/SMOKE.md` | ゴールに向けた実装と、動く状態への収束まで。PR は作らない |
| `/poc-smoke` | `.poc/GOAL.md`、起動中のアプリ URL | `.poc/smoke/round-N/`・判定 | 実機探索・証跡収集・分類・判定。コードは変更しない |
| `/poc-ship` | 現在のブランチ | PR | PR 作成のみ。history / ai-memory / 日報は更新しない |

## agent

`poc-flow:poc-smoke-explorer` — `dev-flow` の `qa-explorer` の軽量版（録画なし・1ゴール20操作打ち切り・`Grep`/`Glob` なし）。起動は必ず**接頭辞付き**で行う。

## 成果物の置き場所

```
.poc/
├── GOAL.md              ← tracked。ゴールと前提。PoC の唯一の仕様書であり、explorer への入力そのもの
├── SMOKE.md             ← tracked。ゴール台帳＋ラウンド記録＋Fix Plan＋判定
├── BACKLOG.md           ← tracked。Friction・未実装ゴール・スコープ外へ逃がした項目
└── smoke/round-N/       ← gitignore。証跡（exploration-log.md / console-messages.md / network-requests.md / screenshots/）
```

## 禁止事項

1. **`.agent/` を作らない。** `dev-flow` の `pre-pr-guard` hook は `REPO_ROOT/.agent/` の存在をスコープガードにしており、これができた瞬間に `/dev-ship` 非経由の `gh pr create` が **exit 2 で恒久的にブロック**される。とくに `hub-run-add.mjs` は `<repo>/.agent/hub-runs/` に書くため**呼んではならない**（dev-hub 連携を失う実害はほぼない。動画・スクショは `~/` 配下の無条件スキャンでインボックスに載る）
2. **`.env` を Write / Edit ツールで書かない。** `pre-edit-protect` hook が全リポでブロックする。`.env.example` を書いて `cp` で複製する
3. **`[dev-flow]` のスキル起動サジェストを無視する。** `suggest-dev-skill.sh` は全リポで発火しマーカーで沈黙させられないので、poc 系スキルは `/poc-*` のスラッシュ起動に統一して回避する
4. **`ALLOW_SECRETS=1` で `git-secret-guard` を回避しない。** 止まったら差分を目視確認してユーザーに判断を仰ぐ
5. **スモークの上限（修正ラウンド3周）を途中で緩めない。** 続けるなら一度打ち切って人間が明示的に再起動する

## PoC ではやらないこと（と、その理由）

| やらないこと | 理由 |
|---|---|
| 自動テスト | テストは仕様を固定する作業だが、PoC は仕様が覆ること自体が目的。固定するたびに書き直しが二重に発生する。回帰検知の受け皿は毎ラウンドの全導線スモークに置く |
| コードレビュー | レビューが守るのは保守性・規約遵守・セキュリティで、いずれも「長く使うコード」に価値が出る |
| 引継書・history・ai-memory・日報 | フェーズ連鎖の概念が無い |
| worktree | 単一ブランチなので main 誤コミット事故が起きない |

**例外はシークレット混入だけ。** 捨てるコードでも git history に残ったトークンは取り返しがつかないので、`git-secret-guard` にそのまま乗る。

## この検査が届かない範囲

スモークが見るのは**主導線のみ**。エッジケース・並行操作・権限境界・データ量による劣化は検知できない。

**「人間が画面を開けるか」も検査しない。** explorer はコンテナ内からアプリを見るので、ポートが公開されていなくても探索は最後まで通り、人間のブラウザだけが `ERR_CONNECTION_REFUSED` になる状態を素通りさせる（実測で踏んだ）。公開ポートの確認は `/poc` の P4 の責務。スモークが全部通っているのに人間が開けないと言われたら、アプリの不具合ではなく**ポート公開を先に疑う**。

**卒業パス**: PoC が本採用に進むと決まった時点で `/dev` に合流する。テストを書くのはそのとき。`.poc/BACKLOG.md` がそのまま `/dev-plan` の入力になる。
